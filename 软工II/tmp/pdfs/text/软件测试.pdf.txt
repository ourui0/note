--- PAGE 14 ---
If software not correct…
• Definitions
• Fault / Defect – The cause of a failure, e.g., a missing or incorrect piece of code
• Error – An intermediate unstable state
• Failure – The manifested inability of the program to perform the function 
required, i.e., a system malfunction evidenced by incorrect output, abnormal 
termination or unmet time and space constraints.
• Relationship
• A fault may remain undetected long time, until some event activates it. 
• If an when the error propagates to the output, it eventually causes the failure.
• Fault  Error  Failure 
• This chain can recursively iterate: a fault in turn can be caused by the failure of 
some other interacting system.

Common V&V Activities
• Static Analysis Techniques –
• Based solely on the (manual or automated) examination of 
project documentation of software models and code, and of 
other related information about requirements and design
• Generally yields valid results, but may be weak in precision
• Dynamic Test Techniques –
• Exercise the software in order to expose possible failures
• Behavioral and performance properties of the program are also 
observed
• Yields more precise results, but only holding for the examined 
executions

桩程序驱动程序
• 桩程序是被测试部件的交互环境，它扮演被测试
部件需要调用的其他系统部件。桩程序对其他系
统部件的扮演仅限于规格相同，内部代码要简单
地多，通常是直接返回固定数据或者按照固定规
则返回数据。
• 驱动程序负责创建被测试部件的执行环境，并驱
动和监控被测试部件执行测试用例的过程，判定
测试用例的执行结果。

系统测试
• 单元测试、集成测试更加关注技术上的正确性，重在发现设计缺陷和代码
缺陷。系统测试则不同，它更关注不符合需求的缺陷和需求自身的内在缺
陷。
• 根据测试目标的不同，有很多不同类型的系统测试：功能测试、非功能性
测试、验收测试、安装测试等等。但是发生在软件测试阶段，完全由软件
测试人员控制和执行的主要是功能测试和非功能性测试。
• 系统测试关注整个系统的行为，所以不依赖于桩程序和驱动程序。但是，
使用一些测试工具可以让系统测试过程更加自动化。
• 系统测试的功能测试计划以需求规格说明文档或用例文档为基础，主要使
用随机测试和基于规格的测试技术设计功能测试用例。在测试非功能性需
求时需要使用针对非功能需求的特定测试技术进行测试计划和测试用例设
计。

测试用例的选择
• 测试的目标是发现尽可能多缺陷， 并不绝对要求所
有。
• 因为测试是有代价的，不仅要耗费桩程序、驱动人力
等成本，更重的是随着测试用例数量增多会直线上升
。
• 所以，软件测试人员需要仔细地选择用例在代价尽可
能小的情况下发现足够多的缺陷 [Zhu1997 ]。
• 测试技术就是帮助软件人员设计和选择用例的。

• 系统需求缺陷、设计缺陷和编码缺陷
• 根据缺陷的影响力
• 严重、一般和无影响

测试智能体（Testing Agent）概述
什么是测试智能体
• 在大模型基础上增加自主规划、工具调用、多步执行能力的自动化测试系
统
• 不只是单纶问答：能持续感知环境、执行动作、观察反馈、迭代优化
• 典型循环：Observe（观察代码/测试结果）→ Plan（制定测试策略）→ Act
（生成/执行测试）→ Reflect（分析失败、改进）
与普通大模型提示词的本质区别
• 普通提示词：单轮输入输出，人工驱动每一步
• 测试智能体：多步自主、工具调用（代码执行 /版本控制/CI）、闭环反馈
• 智能体可跨越多个文件、模 块，端到端完成「发现问题→生成测试→修复
→验证」
智能体在软件工程中的定位
• 人工层：需求分析、测试策略定义、最终审核 —— Human-in-the-Loop
• 智能体层：测试用例生成、执行、失败分析、修复循环、报告生成
• 工具层：测试框架、代码分析器、 CI/CD、覆盖率工具等

测试智能体的核心技能（Skills）
Skill 1：代码理解与调用图分析
• 解析函数调用链、数据流，识别模块间依赖
• 工具：Tree-sitter 语法解析 + 大模型语义理解，建立调用图做测试范围判断
Skill 2：测试用例自动生成
• 基于函数签名、文档注释、已有测试自动补充新用例
• 覆盖正常路径、边界值、异常场景，生成参数化测试（@pytest.mark.parametrize
/ JUnit @ParameterizedTest）
Skill 3：测试执行与自修复（Self-Repair）
• 调用 pytest/JUnit 等执行测试，捕获失败信息
• 分析报错 Traceback，定位根因，自动修改测试或被测代码，迭代直到通过
• 典型案例：SWE-agent 在 SWE-bench 上实现自主修复循环，无需人工介入
Skill 4：缺降定位与根因分析
• 将失败测试映射到源码位置，生成最小复现用例
• 推断是测试写错还是被测代码存在缺降，给出修复建议
Skill 5：覆盖率驱动补全
• 读取覆盖率报告（lcov/coverage.py），识别未覆盖分支
• 针对空白分支自动生成测试，迭代直到覆盖率达到预设阈值

Claude Code 测试 Skills 配置实例
CLAUDE.md：为项目定制测试智能体行为
• 在项目根目录创建 CLAUDE.md，声明测试规范，Claude Code 每次启动自动加载
• # 测试规范
• - 测试框架：pytest + pytest-cov；Mock 使用 unittest.mock
• - 覆盖率要求：语句覆盖 >= 80%，分支覆盖 >= 70%
• - 禁止在测试中使用真实数据库，统一使用fixtures/conftest.py 中的内存 DB
• - 生成测试后必须运行pytest -x 验证，失败则自动修复再提交
自定义 Slash 命令：/test-gen
• 在 .claude/commands/ 目录创建 test-gen.md，定义专属测试生成命令
• # /test-gen
• 读取 $ARGUMENTS 指定的 Python 文件，分析所有public 函数，
• 为每个函数生成3 类测试：正常用例、边界值用例、异常用例，
• 输出到 tests/ 目录，命名规则 test_[原文件名].py，最后运行 pytest 验证。
• 使用方式：在项目内执行 /test-gen src/user_service.py
Hooks：测试自动触发（settings.json）
• "hooks": { "PostToolUse": [{ "matcher": "Write",
• "hooks": [{ "type": "command",
• "command": "pytest tests/ -x -q 2>&1 | tail -5" }] }] }
• 每次 Claude Code 写入文件后自动运行测试，输出最后 5 行结果，失败则进入修复循环

测试智能体端到端工作流示例
场景：CI 流水线中一个失败的集成测试
• 触发：PR 提交后 CI 检测到 1 个 Test Failure，智能体自动介入
Step 1   感知（Observe）
• 读取失败日志、Traceback，定位涉及文件与函数
• 拉取相关代码上下文（调用链± 3 层），建立问题全貌
Step 2   规划（Plan）
• 判断：是测试断言错误、接口变更，还是被测逻辑Bug？
• 制定修复策略：优先修复被测代码，同步更新测试
Step 3   行动（Act）
• 生成修复 Patch 或新测试用例，调用 pytest 执行验证
• 若仍失败：分析新的 Traceback，进入下一轮迭代（平均2-4 轮收敛）
Step 4   反思与提交（Reflect & Commit）
• 所有测试通过后，生成Commit Message，提交 Draft PR
• 附带：变更说明、受影响测试列表、覆盖率变化报告
Human-in-the-Loop 检查点
• 人工 Review：PR 内容、测试充分性、逻辑正确性—— 最终合并决策由人完成

测试智能体的局限与最佳实践
主要局限
• 幻觉风险：生成的测试看似合理但断言错误，造成覆盖率高但扫错能力弱（Test
Oracle Problem）
• 上下文窗口限制：大型代码库中跨文件推理能力下降，易遗漏全局约束
• 环境依赖：测试执行需真实沙盒，配置复杂（数据库、外部服务Mock）
• 可维护性：生成的测试风格不统一，长期维护成本需评估
Human-in-the-Loop（HITL）最佳实践
• 智能体负责「生成+初步验证」，人工负责「策略定义+最终审核」
• 关键模块（安全/支付）保留人工测试用例，不完全依赖智能体
• 建立测试质量门禁：覆盖率、变异测试分数（Mutation Score）作为 HITL 触发阈
值
与 CI/CD 融合的推荐架构
• PR 提交 → 智能体自动补全测试 → CI 执行 → 覆盖率不足则智能体继续迭代
• 将智能体生成的测试纳入版本控制，与手工测试统一管理
评估测试智能体质量的维度
• 缺降检出率（Mutation Score）、覆盖率增量、误报率、用例可读性
