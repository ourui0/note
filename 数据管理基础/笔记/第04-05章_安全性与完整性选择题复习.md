# 第04-05章 数据库安全性与完整性选择题复习

参考：第04章、第五章讲义，以及 `documents-export-2026-6-17` 中 2016 样卷、2020 A 卷、2023 回忆。

说明：这两章大概率只在选择题或零散 SQL/视图题中考察，复习重点是概念辨析和关键命令，不按大题深挖。

## 一、往年卷出现过的考点

往年题中和第04、05章相关的高频点：

- 视图的定义、作用、优点。
- `WITH CHECK OPTION` 的含义。
- 哪些视图可更新，哪些不可更新。
- `GRANT` / `REVOKE`：授权与回收权限。
- 数据安全性 vs 数据完整性。
- 封锁机制属于并发控制，不是安全性/完整性控制。
- 外码 / 参照完整性。
- `PRIMARY KEY`、`FOREIGN KEY`、`UNIQUE`、`NOT NULL`、`CHECK`。
- 外码违约处理：`CASCADE`、`RESTRICT`、`SET NULL`。
- 触发器是动态约束。
- 断言是表外独立定义的全局约束。

## 二、第04章 数据库安全性

### 1. 什么是数据库安全性

数据库安全性是指：

```text
保护数据库，防止不合法使用所造成的数据泄露、更改或破坏。
```

防范对象：

```text
非法用户、非法操作、恶意破坏、敏感数据泄露
```

注意区分：

```text
安全性：防非法用户和非法操作。
完整性：防不正确、不合语义的数据。
```

例：

- 用户无权限查看工资表：安全性问题。
- 学生成绩为 150 分：完整性问题。
- 学生所在院系号不存在：完整性问题。
- 黑客盗取用户口令：安全性问题。

### 2. 数据库保护的四类问题

数据库系统常见破坏来源：

- 非法用户。
- 非法数据。
- 各种故障或误操作。
- 多用户并发访问。

对应保护措施：

| 问题 | 保护措施 |
| --- | --- |
| 非法用户 / 非法操作 | 安全性保护，权限管理 |
| 非法数据 / 不合语义数据 | 完整性保护 |
| 故障或误操作 | 故障恢复 |
| 并发访问冲突 | 并发控制 |

往年易错选择：

```text
封锁机制是并发控制的主要方法，不是安全性控制，也不是完整性控制。
```

### 3. 数据库安全控制常用方法

常用安全性控制方法：

- 用户标识和鉴定。
- 存取控制。
- 视图机制。
- 审计。
- 数据加密。

### 4. 用户身份鉴别

用户身份鉴别是系统提供的最外层安全保护措施。

常见方法：

- 静态口令。
- 动态口令，一次一密。
- 生物特征，如指纹、虹膜。
- 智能卡。

### 5. 存取控制

存取控制机制包括两部分：

1. 定义用户权限，并登记到数据字典中。
2. 用户发出访问请求时，DBMS 根据授权规则做合法权限检查。

权限组成：

```text
数据库对象 + 操作类型
```

例如：

```text
对 Student 表有 SELECT 权限
对 Student 表的 Sage 列有 UPDATE 权限
```

### 6. DAC 与 MAC

自主存取控制 DAC：

- Discretionary Access Control。
- 自 C1 级开始要求提供。
- 用户对不同对象有不同权限。
- 不同用户对同一对象也可有不同权限。
- 用户可将自己拥有的权限转授给其他用户。
- SQL 中主要通过 `GRANT`、`REVOKE` 支持。

强制存取控制 MAC：

- Mandatory Access Control。
- 自 B1 级开始要求提供。
- 每个数据对象有密级。
- 每个用户有许可证级别。
- 只有具备合法许可证的用户才能存取相应对象。

选择题抓手：

```text
DAC：用户自主授权，GRANT/REVOKE。
MAC：密级 + 许可证，强制控制。
```

### 7. GRANT 与 REVOKE

`GRANT`：授予权限。

```sql
grant select on Student to U1;
```

`REVOKE`：回收权限。

```sql
revoke select on Student from U1;
```

样卷选择题：

```text
从用户那里回收访问权限的 SQL 命令动词是 REVOKE。
```

常见权限：

- `SELECT`
- `INSERT`
- `UPDATE`
- `DELETE`
- `REFERENCES`
- `ALL PRIVILEGES`

数据库对象权限例子：

- 表和视图：`SELECT`、`INSERT`、`UPDATE`、`DELETE`、`REFERENCES`。
- 属性列：`SELECT`、`INSERT`、`UPDATE`、`REFERENCES`。

### 8. 角色

角色是权限的集合。

作用：

- 简化权限管理。
- 可把权限授予角色，再把角色授予用户。

记忆：

```text
用户很多、权限相似时，用角色集中管理。
```

### 9. 视图机制

视图是从一个或多个基本表或其他视图导出的虚表。

视图本身通常不单独存储数据，只保存定义。

视图作用：

- 提供数据逻辑独立性。
- 简化用户操作。
- 使用户从多角度看同一数据。
- 提供一定安全保护，只暴露允许用户看到的数据。

往年选择题：

```text
视图的优点之一是提高数据的逻辑独立性。
```

注意：

```text
视图通常不能直接提高查询效率。
```

如果选项有：

- 提高数据逻辑独立性：对。
- 提高查询效率：一般不选。
- 节省存储空间：视图本身一般不存数据，但这不是最核心、最稳妥选项。

### 10. WITH CHECK OPTION

`WITH CHECK OPTION` 用在视图创建中。

作用：

```text
保证通过视图插入或修改的数据，仍然满足视图定义中的查询条件。
```

也就是说：

```text
通过视图写入的数据，写完后仍能通过该视图被查询到。
```

2016 样卷考点：

```text
WITH CHECK OPTION 的作用不是检查视图创建权限，也不是检查查询权限；
而是确保通过视图写入的数据也能通过该视图被访问到。
```

例：

```sql
create view CS_S as
select sno, sname, age
from S
where dept = '计算机系'
with check option;
```

若通过该视图插入一个非计算机系学生，应被拒绝。

### 11. 视图更新

不是所有视图都可更新。

通常可更新的视图：

- 基于单个基本表。
- 不包含聚集函数。
- 不包含 `GROUP BY`。
- 不包含去重、集合运算等复杂操作。
- 视图中包含足够定位原表元组的属性。

通常不可更新的视图：

- 含聚集函数，如 `AVG`、`SUM`。
- 含 `GROUP BY`。
- 含多表连接且无法唯一对应基表元组。
- 含表达式列、计算列。

2020 往年题例：

```sql
CREATE VIEW CS_S AS
SELECT S#, SNAME, AGE
FROM S
WHERE SD='计算机系';
```

对 `CS_S` 更新已有学生姓名：

```sql
UPDATE CS_S
SET SNAME='WANG PING'
WHERE S#='200801001';
```

通常可以执行，因为它来自单表，且更新的是原表中的普通属性。

但：

```sql
CREATE VIEW S_G(S#, GAVG) AS
SELECT S#, AVG(GRADE)
FROM SC
GROUP BY S#;
```

对 `S_G` 更新平均成绩：

```sql
UPDATE S_G SET GAVG=85 WHERE S#='200801001';
```

不能执行，因为 `GAVG` 是聚集计算结果，不对应单个基表元组的可直接更新列。

往年判断：

```text
“所有视图都可以插入数据”是错的。
```

### 12. 审计与加密

审计：

- 记录用户对数据库的操作。
- 形成审计日志。
- 用于事后检查、追踪异常行为、安全分析。

数据加密：

- 防止敏感数据泄露。
- 可用于数据存储加密和传输加密。

## 三、第05章 数据库完整性

### 1. 什么是数据库完整性

数据库完整性是指数据的：

- 正确性：符合现实世界语义。
- 相容性：同一对象在不同表中的数据逻辑一致。

例：

- 学号必须唯一。
- 性别只能是男或女。
- 年龄在合理范围内。
- 学生选的课程必须存在。
- 学生所在院系必须存在。

### 2. 完整性 vs 安全性

| 项目 | 完整性 | 安全性 |
| --- | --- | --- |
| 目标 | 防止不正确、不合语义的数据 | 防止非法访问、恶意破坏 |
| 防范对象 | 非法数据 | 非法用户和非法操作 |
| 例子 | 成绩不能超过 100 | 无权限用户不能查工资 |

选择题常见陷阱：

```text
防止非法用户访问数据库：安全性。
防止数据库中出现不合语义数据：完整性。
```

### 3. 完整性机制三部分

DBMS 完整性机制包括：

1. 提供定义完整性约束条件的机制。
2. 提供完整性检查的方法。
3. 违约处理。

完整性检查通常发生在：

- `INSERT`
- `UPDATE`
- `DELETE`

之后，也可以在事务提交时检查。

违约处理：

- 拒绝操作：`NO ACTION` / `RESTRICT`。
- 级联执行相关操作：`CASCADE`。
- 置空：`SET NULL`。

### 4. 三类完整性

关系模型中的完整性通常包括：

- 实体完整性。
- 参照完整性。
- 用户定义完整性。

### 5. 实体完整性

实体完整性要求：

```text
主码属性不能为空，且主码值唯一。
```

SQL 定义：

```sql
primary key
```

或：

```sql
unique + not null
```

违约检查：

- 插入或更新主码时检查唯一性。
- 主码任何组成列为空都拒绝。

注意：

```text
主码不能取空值。
```

如果往年题说“主属性的值不能为空”，要小心：严格说是“主码属性不能空”。主属性是出现在候选码中的属性，若未被选为主码，在 SQL 中是否允许空要看约束定义；考试简单题常把主码属性当重点。

单列主码可以列级定义：

```sql
Sno char(9) primary key
```

复合主码必须表级定义：

```sql
primary key (sno, cno)
```

### 6. 参照完整性

参照完整性用于保证外码引用的对象存在。

外码：

```text
本表中引用另一个表主码/候选码的属性或属性组。
```

例：

```text
学生(学号, 姓名, 院系号)
院系(院系号, 院系名)
```

`学生.院系号` 是外码，引用 `院系.院系号`。

SQL：

```sql
foreign key (deptno) references Dept(deptno)
```

或列级：

```sql
deptno references Dept(deptno)
```

参照完整性要求：

```text
外码值要么为空，要么等于被引用关系中某个候选码/主码值。
```

是否允许空值取决于该外码列是否定义了 `NOT NULL`。

### 7. 外码违约处理规则

当删除或更新被引用表中的主码值时，可能造成子表外码悬空。

常见处理：

```text
CASCADE
RESTRICT
SET NULL
NO ACTION
```

含义：

- `CASCADE`：级联删除或级联更新相关子表记录。
- `RESTRICT`：若存在引用，则拒绝删除或更新。
- `SET NULL`：把子表对应外码设置为空。
- `NO ACTION`：不执行该违约操作，效果常接近拒绝。

样卷选择题：

```text
不是外码约束违约处理规则的是 CHECK。
```

### 8. 用户定义完整性

用户定义完整性是针对具体应用语义的约束。

例：

- 性别只能是 `男` 或 `女`。
- 年龄在 14 到 50 之间。
- 成绩在 0 到 100 之间。
- 学分必须大于 0。

常用 SQL：

```sql
not null
unique
check
default
```

例：

```sql
grade int check (grade between 0 and 100)
```

### 9. 完整性约束分类

按定义对象分类：

1. 与表有关的约束。
2. 域约束。
3. 断言。

与表有关的约束包括：

- `PRIMARY KEY`
- `FOREIGN KEY`
- `UNIQUE`
- `NOT NULL`
- `CHECK`
- `DEFAULT`

按定义位置分类：

- 列级约束：定义在单个列后面。
- 表级约束：单独作为表定义的一部分，可涉及多个列。

复合主码、复合外码、多列 `CHECK` 通常用表级约束。

### 10. 静态约束与动态约束

静态约束：

```text
要求数据库在任何时候都满足的约束。
```

例如：

- 表约束。
- 域约束。
- 断言。

动态约束：

```text
数据库状态变化时要满足的约束。
```

例如：

- 触发器。

### 11. 断言

断言 `Assertion`：

- 是一个谓词表达式。
- 表达希望数据库总能满足的条件。
- 可与一个或多个表关联。
- 可理解为跨多个表的全局 `CHECK` 约束。
- 必须在表定义之外独立创建。

选择题抓手：

```text
断言不是 CREATE TABLE 中的单表约束；
它适合表达跨表全局约束。
```

### 12. 触发器

触发器是动态约束机制。

用途：

- 细分完整性检查条件。
- 检查数据完整性。
- 自动执行某些数据处理。
- 实现业务逻辑。

触发事件通常包括：

- `INSERT`
- `UPDATE`
- `DELETE`

选择题抓手：

```text
触发器不是在基表 CREATE TABLE 命令中定义的普通约束。
```

2026 样卷中：

```text
不在基表创建命令中定义的是：触发器。
```

### 13. 约束命名

可以用 `CONSTRAINT` 给约束命名。

例：

```sql
constraint pk_student primary key (sno)
```

作用：

- 便于后续删除、修改、报错定位。

## 四、往年选择题速记

### 1. 视图优点

题：视图的优点之一是？

优先选：

```text
提高数据的逻辑独立性
```

不要选：

```text
提高查询效率
```

### 2. 视图不能完成的操作

题：在视图上不能完成的操作是？

常见答案：

```text
在视图上定义新的基本表
```

视图可以查询；某些简单视图可以更新；可以基于视图再定义视图。

### 3. 所有视图都可以插入数据

判断：

```text
错。
```

聚集视图、分组视图、多表复杂视图通常不可插入/更新。

### 4. WITH CHECK OPTION

题：视图创建中 `WITH CHECK OPTION` 作用？

答案：

```text
确保通过视图写入的数据也能通过该视图被访问到。
```

### 5. 封锁机制

题：数据库中封锁机制是什么的主要方法？

答案：

```text
并发控制
```

不是完整性控制，也不是安全性控制。

### 6. REVOKE

题：从用户那里回收访问权限的 SQL 命令？

答案：

```text
REVOKE
```

### 7. 外码违约处理

题：不是外码约束违约处理规则的是？

答案：

```text
CHECK
```

常见外码违约处理：

```text
CASCADE, RESTRICT, SET NULL, NO ACTION
```

### 8. 触发器

题：哪些约束不是在 `CREATE TABLE` 中定义？

常见答案：

```text
触发器
```

`PRIMARY KEY`、`FOREIGN KEY`、`NOT NULL`、`CHECK` 都可在建表时定义。

### 9. 完整性约束类型

题：完整性约束有哪几种？

可答：

```text
实体完整性、参照完整性、用户定义完整性。
```

从 SQL 定义角度：

```text
表约束、域约束、断言；触发器用于动态约束。
```

## 五、易混点总表

| 概念 | 关键词 | 易错点 |
| --- | --- | --- |
| 安全性 | 非法用户、非法操作、权限、泄露 | 不等于完整性 |
| 完整性 | 正确性、相容性、语义约束 | 不负责防黑客 |
| DAC | 自主、GRANT、REVOKE、可转授权 | C1 开始要求 |
| MAC | 密级、许可证、强制控制 | B1 开始要求 |
| 视图 | 虚表、逻辑独立性、安全保护 | 不一定提高效率 |
| WITH CHECK OPTION | 通过视图写入后仍满足视图条件 | 不是权限检查 |
| 实体完整性 | 主码唯一且非空 | 复合主码任一列都不能为空 |
| 参照完整性 | 外码引用已存在主码/候选码 | 外码可否为空看定义 |
| 用户定义完整性 | `CHECK`、`NOT NULL`、范围限制 | 应用语义约束 |
| 触发器 | 动态约束、事件触发 | 不是普通建表约束 |
| 断言 | 跨表全局条件 | 表定义之外独立创建 |
| 封锁 | 并发控制 | 不是安全性控制 |

## 六、考前只背版

```text
安全性：防非法用户/非法操作。
完整性：防不正确/不合语义数据。
```

```text
安全控制：身份鉴别、存取控制、视图、审计、加密。
```

```text
DAC：GRANT/REVOKE，自主授权。
MAC：密级 + 许可证，强制控制。
```

```text
视图优点：逻辑独立性、安全保护、简化操作。
WITH CHECK OPTION：通过视图写入的数据仍能被视图查到。
```

```text
完整性三类：实体完整性、参照完整性、用户定义完整性。
实体完整性：主码唯一且非空。
参照完整性：外码引用存在的主码/候选码。
用户定义完整性：NOT NULL、UNIQUE、CHECK、DEFAULT 等。
```

```text
外码违约处理：CASCADE、RESTRICT、SET NULL、NO ACTION。
CHECK 不是外码违约处理。
```

```text
触发器：动态约束，不是在 CREATE TABLE 中定义的普通约束。
封锁：并发控制。
```
