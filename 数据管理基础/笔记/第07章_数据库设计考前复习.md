# 第07章 数据库设计考前复习

参考：第07章讲义、复习思考题、数据库设计案例、数据管理基础期末练习（2026）。

## 一、样卷考法

第07章样卷大题考数据库设计：

- 从需求文字中抽取实体、属性、联系。
- 画出或文字描述 EER 模型。
- 判断多值属性、弱实体、ISA 联系。
- 标注基数约束。
- 将 EER 模型转换成关系模式。
- 写出每个关系的候选码。

样卷高铁乘务组题还特别考：

- ISA 分类：列车长、乘警、乘务员。
- 每天每趟车的运行任务：`车次号 + 行驶日期`。
- 一对一 / 一对多人员安排。

## 二、数据库设计过程

数据库设计六个阶段：

1. 需求分析。
2. 概念结构设计。
3. 逻辑结构设计。
4. 物理结构设计。
5. 数据库实施。
6. 数据库运行和维护。

各阶段结果：

- 需求分析：需求分析说明书、数据字典。
- 概念结构设计：独立于 DBMS 的概念模型，常用 ER/EER 图。
- 逻辑结构设计：转换为某 DBMS 支持的逻辑模型，如关系模式。
- 物理结构设计：存储结构、存取方法、索引等。
- 数据库实施：建库、装载数据、调试程序。
- 运行和维护：备份恢复、性能调整、重组织、重构造。

样卷选择题：关系规范化设计属于逻辑结构设计阶段。

## 三、ER / EER 基本概念

实体：

客观存在并可相互区别的对象。

属性：

描述实体或联系的数据项。

属性域：

属性可能取值的范围。

实体集：

具有相同实体型的一组实体。

标识符：

能唯一标识实体实例的属性或属性组，对应关系数据库中的候选码。

描述符：

非键属性，用来描述实体或联系。

联系：

实体之间或实体内部的对应关系。

联系实例：

某一次具体发生的联系，对应一组实体实例。

## 四、属性类型

单值属性：

每个实体实例只取一个值。

组合属性：

由多个成员属性组成。例如姓名可拆成姓、名；地址可拆成省、市、街道。

多值属性：

一个实体实例可取多个值。例如读者联系电话、学生手机号。

转换规则：

- 单值属性：直接作为列。
- 组合属性：展开为多个成员列。
- 多值属性：单独转换成关系。

例：

```text
读者(借书证号, 姓名, 身份证号, 联系电话)
```

若联系电话是多值属性，应转为：

```text
读者(借书证号, 姓名, 身份证号)
读者电话(借书证号, 联系电话)
```

`读者电话` 的候选码通常是：

```text
(借书证号, 联系电话)
```

## 五、联系与基数约束

联系按参与实体型个数：

- 一元联系：同一实体集内部的联系。
- 二元联系：两个实体集之间的联系。
- 多元联系：三个或更多实体集之间的联系。

函数关系：

- 1:1
- 1:n
- m:n

基数约束 `min..max`：

- `0..1`：可不参与，最多一次。
- `1..1`：必须参与，且只能一次。
- `0..*`：可不参与，可多次。
- `1..*`：必须至少一次，可多次。

参与方式：

- `min = 1`：强制参与。
- `min = 0`：非强制参与。
- `max = 1`：单值参与。
- `max = *`：多值参与。

例：

```text
教师 负责 课程
教师端：0..*
课程端：1..1
```

含义：

- 教师可以不负责课程，也可以负责多门课程。
- 每门课程必须且仅由一位教师负责。

## 六、弱实体

弱实体：

存在依赖于其他实体，不能脱离强实体独立存在。

典型特征：

- 自身只有局部标识符。
- 完整标识需要依附实体的主码。

例：

```text
课程项目依附于课程
同一门课程内项目编号唯一，不同课程可有相同项目编号
```

关系模式：

```text
课程(课程号, 课程名)
课程项目(课程号, 项目编号, 项目名称, 截止日期)
```

`课程项目` 的候选码：

```text
(课程号, 项目编号)
```

## 七、ISA 联系

ISA 表示父类-子类语义，即 “is a”。

性质：

- 子类继承父类所有属性。
- 子类可有自己的属性。
- 子类也可继续有子类。

约束：

- 不相交：一个父类实体最多属于一个子类。
- 可重叠：一个父类实体可同时属于多个子类。
- 完全特化：父类中每个实体必须属于某个子类。
- 部分特化：父类中某些实体可不属于任何子类。

例：样卷高铁乘务组。

```text
人员(身份证号, 姓名, 联系电话)
列车长 is a 人员
乘警 is a 人员
乘务员 is a 人员
```

其中：

- 列车长、乘警有 `入职日期`。
- 乘务员有 `派遣公司名称, 聘用日期`。

## 八、EER 转关系模式规则

### 规则1：实体集

每个实体集转换成一个关系。

```text
学生(学号, 姓名)
```

标识符成为候选码或主码。

### 规则2：多值属性

每个多值属性单独成表。

```text
学生(学号, 姓名)
学生手机号(学号, 手机号)
```

`学生手机号` 的候选码：

```text
(学号, 手机号)
```

### 规则3：1:1 联系

按参与约束决定：

- 两端非全参与：转 3 个关系。
- 一端全参与：联系合并到全参与端。
- 两端全参与：可合并成 1 个关系。

例：

```text
人 0..1 -- 拥有 -- 1..1 驾驶证
```

驾驶证全参与，合并到驾驶证：

```text
人(身份证号, 姓名)
驾驶证(档案编号, 准驾车型, 有效期限, 身份证号)
```

### 规则4：1:n 联系

通常合并到 n 端，在 n 端加入 1 端主码作为外码。

例：

```text
教师 0..* -- 负责 -- 1..1 课程
```

每门课程必须由一位教师负责：

```text
教师(工号, 姓名, 职称)
课程(课程号, 课程名, 学分, 负责教师工号)
```

### 规则5：m:n 联系

m:n 联系必须单独成表。

例：

```text
学生 -- 选修 -- 课程
联系属性：成绩
```

关系模式：

```text
学生(学号, 姓名)
课程(课程号, 课程名)
选修(学号, 课程号, 成绩)
```

`选修` 的候选码：

```text
(学号, 课程号)
```

### 规则6：多元联系

多元联系通常单独成表，包含各实体主码和联系属性。

例：

```text
供应(供应商号, 项目号, 零件号, 供应量)
```

候选码通常是参与实体主码组合，但最终要结合语义和规范化判断。

### 规则7：单实体集内部的联系

需要给不同角色的外码改名。

例：职工上下级。

```text
职工(工号, 姓名, 上级职工工号)
```

其中：

- `工号` 是主码。
- `上级职工工号` 是外码，引用 `职工(工号)`。

### 规则8：ISA 联系

常见三种转换：

方式1：父类和每个子类都建表。

```text
人员(身份证号, 姓名, 联系电话)
列车长(身份证号, 入职日期)
乘警(身份证号, 入职日期)
乘务员(身份证号, 派遣公司名称, 聘用日期)
```

方式2：只建叶子子类表，继承父类属性。

适合不相交且完全特化。

方式3：合并成一个大表。

简单但空值多，约束弱。

考试建议：如果题目明显考 EER / ISA，优先用方式1，更清晰。

## 九、例题1：图书借阅管理

需求摘要：

- 图书：书号、书名。书号唯一，书名可重复。
- 读者：借书证号、身份证号、姓名、居住地址、联系电话。
- 借书证号和身份证号都可标识读者。
- 联系电话是多值属性。
- 出版社：出版社名称、办公地址、联系电话。
- 每本书由一个出版社出版。
- 读者可多次借同一本书，要保存借阅历史，记录借阅日期和归还日期。

EER 要点：

- 图书、读者、出版社是实体。
- 读者联系电话是多值属性。
- 出版社与图书是 1:n。
- 借阅是读者与图书之间的联系，带属性 `借阅日期, 归还日期`。
- 因为同一读者可不同时间借同一本书，借阅关系的码不能只用 `(借书证号, 书号)`。

关系模式：

```text
读者(借书证号, 身份证号, 姓名, 居住地址)
读者电话(借书证号, 联系电话)
出版社(出版社名称, 办公地址, 联系电话)
图书(书号, 书名, 出版社名称)
借阅(借书证号, 书号, 借阅日期, 归还日期)
```

候选码：

```text
读者：借书证号；身份证号
读者电话：(借书证号, 联系电话)
出版社：出版社名称
图书：书号
借阅：通常可用 (书号, 借阅日期)；也可根据语义讨论 (书号, 归还日期)
```

典型函数依赖：

```text
借书证号 -> 身份证号, 姓名, 居住地址
身份证号 -> 借书证号, 姓名, 居住地址
书号 -> 书名, 出版社名称
出版社名称 -> 办公地址, 联系电话
(书号, 借阅日期) -> 借书证号, 归还日期
```

为什么不是 `(借书证号, 书号) -> 借阅日期, 归还日期`：

同一读者可在不同时候借同一本书，所以 `(借书证号, 书号)` 相同的记录可以有多个借阅日期。

## 十、例题2：考试监考安排

需求摘要：

- 课程：课程号、课程名。
- 教师：工作证编号、姓名。
- 教室：考试教室。
- 每门课程至少一位主讲教师。
- 每门课期末考试一场，考试时间包括开始和结束时间，可分多个教室同时进行。
- 同一时间，一间教室只能安排一门课程考试。
- 主讲教师必须作为主考教师参加自己主讲课程监考。
- 每间教室还需安排一位或多位监考老师。

建模要点：

- 主讲、主考、监考是不同联系/角色。
- 考试安排要包含课程、时间、教室。
- 教师在同一时间只能在一个教室监考。

若简化成关系：

```text
监考安排(cno, sdate, room, tno)
```

常见函数依赖：

```text
cno -> sdate
(sdate, room) -> cno
(sdate, tno) -> room
```

候选码：

```text
(tno, cno)
(tno, sdate)
```

最高范式：

```text
3NF，不满足 BCNF
```

原因：

`cno -> sdate` 中 `cno` 不是超码，但 `sdate` 是主属性，所以满足 3NF，不满足 BCNF。

## 十一、例题3：样卷高铁乘务组

需求摘要：

- 高铁：车次号、始发站、始发时间、终点站、终点到达时间。
- 人员：身份证号、姓名、联系电话。
- 列车长、乘警是固定铁路员工，有入职日期。
- 乘务员是劳务派遣人员，有派遣公司名称、聘用日期。
- 每个乘务组由 1 名列车长、若干乘警、若干乘务员组成。
- 每天每趟高铁要记录行驶日期和乘务组安排。
- 同一趟高铁每天乘务组不固定，但一次运行过程中组成人员不变。

更严谨的 EER：

- `人员` 是父实体。
- `列车长`、`乘警`、`乘务员` 是子实体。
- `高铁` 与 `列车运行`：一趟高铁每天可有一次运行。
- `列车运行` 与三类人员分别建立安排联系。

推荐关系模式：

```text
高铁(车次号, 始发站, 始发时间, 终点站, 终点到达时间)
人员(身份证号, 姓名, 联系电话)
列车长(身份证号, 入职日期)
乘警(身份证号, 入职日期)
乘务员(身份证号, 派遣公司名称, 聘用日期)
列车运行(车次号, 行驶日期)
乘务组列车长(车次号, 行驶日期, 列车长身份证号)
乘务组乘警(车次号, 行驶日期, 乘警身份证号)
乘务组乘务员(车次号, 行驶日期, 乘务员身份证号)
```

候选码：

```text
高铁：车次号
人员：身份证号
列车长：身份证号
乘警：身份证号
乘务员：身份证号
列车运行：(车次号, 行驶日期)
乘务组列车长：(车次号, 行驶日期)
乘务组乘警：(车次号, 行驶日期, 乘警身份证号)
乘务组乘务员：(车次号, 行驶日期, 乘务员身份证号)
```

说明：

- `乘务组列车长` 的码是 `(车次号, 行驶日期)`，因为每个乘务组只有一名列车长。
- `乘务组乘警` 和 `乘务组乘务员` 是多值参与，所以码要加人员身份证号。
- 样卷参考答案把人员合并成一个 `职工` 表，是简化写法；严格 EER 建议拆出 ISA 子类。

## 十二、物理设计与维护速查

物理设计内容：

- 选择存取方法。
- 设计存储结构。
- 评价时间和空间效率。

常用存取方法：

- B+树索引。
- Hash 索引。
- 聚簇。

B+树索引适合：

- 查询条件经常出现的属性。
- 连接条件经常出现的属性。
- 经常求最大值、最小值的属性。

Hash 适合：

- 等值查询。
- 等值连接。

聚簇适合：

- 经常按某属性查询大量相关元组。
- 经常连接的关系。

数据库维护：

- 转储和恢复。
- 安全性、完整性控制。
- 性能监督、分析和改进。
- 重组织：不改变逻辑结构和物理结构，重新安排存储、回收空间。
- 重构造：应用环境变化后，调整模式和内模式。

## 十三、考前建模检查清单

做数据库设计题时逐项检查：

1. 每个实体是否有标识符？
2. 有没有多值属性？是否单独成表？
3. 有没有组合属性？是否拆开？
4. 有没有弱实体？主码是否包含强实体主码？
5. 有没有 ISA？是否需要父类和子类分别建表？
6. 1:n 联系是否合并到 n 端？
7. m:n 联系是否单独成表？
8. 联系上的属性是否放到联系关系中？
9. 递归联系的外码是否改名表达角色？
10. 每个关系的候选码是否写全？

## 十四、转换规则速查

```text
实体集 -> 一个关系
组合属性 -> 展开成多个列
多值属性 -> 单独关系
1:1 联系 -> 看参与约束，可 1/2/3 个关系
1:n 联系 -> 通常合并到 n 端
m:n 联系 -> 单独关系
多元联系 -> 单独关系
弱实体 -> 主码 = 强实体主码 + 局部码
ISA -> 父表 + 子表最稳
```
