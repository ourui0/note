什么是模块（Module）
A module is a self-contained unit of software that can be
independently designed, implemented, and tested.
在⾯向对象中，模块有三种粒度：
粒度 对应构件 职责边界
⽅法级 Method / Function 单⼀操作
类级 Class 状态 + ⾏为
包级 Package / Namespace 相关类集合
模块化的两个核⼼指标
耦合（Coupling）
模块之间的依赖强度
→ 越低越好
内聚（Cohesion）
模块内部元素的关联程度
→ 越⾼越好
设计⽬标：⾼内聚、低耦合

⾯向对象的耦合类型
在 O O  系统中，耦合来⾃两个⽅向：
访问耦合
Component Coupling
类 A 使⽤类 B 的服务时产⽣
调⽤⽅法
访问字段
作为参数传递
通过消息链跨越多跳

⽗类修改可能破坏⼦类

继承是"⽩盒复⽤"——⼦类可以看到⽗类的内部实现；访问耦合是"⿊盒复⽤"——只依赖接⼝。

Cascading Message（消息链）问题
// 问题代码：消息链（ Train Wreck ）
String city = customer
    .getAddress()
    .getCity()
    .toUpperCase();
问题：Customer 的调⽤⽅知道了：
Customer 有 Address
Address 有 City
City 是 String
三层实现细节全部暴露！
两种修复⽅案
⽅案 A：引⼊局部变量
Address addr = customer.getAddress();
City city = addr.getCity();
String name = city.toUpperCase();
可读性提升，但耦合依然存在。
⽅案 B：委托（推荐）
// 在  Customer 中封装
String city = customer.getCityName();
调⽤⽅只需知道 Customer 。

P5 · 迪⽶特法则（Law of Demeter）
只与你的直接朋友交谈。
A method should only call methods on: itself, its parameters, objects it creates, and its direct ﬁelds.
合法的调⽤对象
1. this （⾃身）
2. ⽅法的参数对象
3. ⽅法内新创建的对象
4. 类的成员变量（直接持有）
违反示例
// 违反：通过  getB() 拿到中间对象再调⽤
a.getB().doSomething();
// 合规：委托给  B 的操作封装在  A 中
a.delegateToB();
迪⽶特法则是对访问耦合级别的直接约束：避免消息链，
减少对间接对象的依赖。

P4 · ⾯向接⼝编程
Program to an interface, not an implementation.
// 不好：依赖具体类
ArrayList<String> list = new ArrayList<>();
// 好：依赖接⼝
List<String> list = new ArrayList<>();
好处：
调⽤⽅只依赖接⼝契约，不依赖实现
切换实现类⽆需修改调⽤⽅
⽀持多态、Mock 测试
⾯向接⼝编程将访问耦合从参数变量级降低到仅依赖接⼝，是降低耦合的核⼼⼿段。

P6 · 接⼝隔离原则（ISP）
Clients should not be forced to depend on interfaces they do not use.
肥接⼝问题
interface Worker {
    void work();
    void eat();    // Robot 不需要！
    void sleep();  // Robot 不需要！
}
class Robot implements Worker {
    public void work() { ... }
    public void eat()  { throw new UnsupportedOperationException(); }
    public void sleep(){ throw new UnsupportedOperationException(); }
}
ISP 重构
interface Workable {
    void work();
}
interface Feedable {
    void eat();
    void sleep();
}
class Robot implements Workable { ... }
class Human implements Workable,
                      Feedable  { ... }
接⼝细化后，Robot 不再被迫实现⽆关⽅
法，调⽤⽅只依赖⾃⼰真正需要的接⼝。

P7 · ⾥⽒替换原则（LSP）
⼦类型必须能够替换其⽗类型⽽不改变程序的正确性。
— Barbara Liskov, 1987
经典反例：正⽅形 ≠ ⻓⽅形
class Rectangle {
    void setWidth(int w)  { ... }
    void setHeight(int h) { ... }
    // 不变式： w 与  h 独⽴
}
class Square extends Rectangle {
    void setWidth(int w) {
        super.setWidth(w);
        super.setHeight(w); // 破坏不变式！
    }
}
为什么违反 L SP？
void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(3);
    // 期望⾯积  = 15
    assert r.area() == 15; // Square 中失败！
}
Square 在⼏何上是 Rectangle 的⼦集，但在⾏为契约
上不能替换。"IS-A" 关系应由⾏为定义，⽽⾮数学定义。
📖  SW EBO K v4 §5.4 · O bject-O riented Design (SO L ID — L iskov Substitution)

--- PAGE 17 ---
LSP 反例：企鹅与⻦
class Bird {
    void fly() { ... }  // 所有⻦都会⻜？
}
class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException(" 企鹅不会⻜！ ");
    }
}
// 调⽤⽅：
void makeBirdFly(Bird b) {
    b.fly(); // Penguin 会抛异常！
}
修复⽅案
interface Flyable {
    void fly();
}
class Sparrow extends Bird
    implements Flyable {
    public void fly() { ... }
}
class Penguin extends Bird {
    // 不实现  Flyable
    void swim() { ... }
}
⽤接⼝分离代替强制继承层次，Penguin 不
再承诺 fly() ，LSP ⾃然满⾜。

--- PAGE 18 ---
LSP 的契约含义
LSP 要求⼦类遵守⽗类的⾏为契约：
契约要素 L SP 要求
前置条件 ⼦类前置条件 ≤ ⽗类（⼦类不能更严格）
后置条件 ⼦类后置条件 ≥ ⽗类（⼦类保证更多）
不变式 ⼦类必须维护⽗类的所有不变式
违反示例（前置条件更严格）
// ⽗类：接受任意正整数
void setAge(int age) { assert age > 0; }
// ⼦类：要求年龄  < 150 （更严格）
void setAge(int age) {
    assert age > 0 && age < 150; // 违反！
}
记忆⼝诀
⼦类前置放宽，后置加强，
不变式维持——这才叫替换。

P8 · 组合优于继承
Favor object composition over class inheritance.
— GoF, Design Patterns, 1994
继承的问题
⽩盒复⽤：⼦类依赖⽗类实现细节
⽗类修改可能破坏所有⼦类
继承层次难以扩展（多个维度变化时）
强迫遵守 IS-A 语义
组合的优势
⿊盒复⽤：只依赖接⼝
运⾏时可动态切换组合对象
职责分离更清晰
⽆需⽗类 IS-A 约束
// 继承： Stack extends Vector （历史错误）
// 组合： Stack 内部持有  Vector
class Stack<T> {
    private Vector<T> storage = new Vector<>();
    public void push(T item) { storage.add(item); }
    public T pop() { return storage.remove(...); }
}

信息隐藏的本质
每个模块应该对其他模块隐藏⼀个重要的设计决策。
— David Parnas, 1972
两类秘密（Secrets）
主要秘密（Primary Secret）
= 职责变更的可能性
→ 这个类应该做什么会变化吗？
次要秘密（Secondary Secret）
= 实现变更的可能性
→ 这个类如何做会变化吗？
为什么要隐藏？
变化是软件的常态。
将变化的可能性封装在模块内部，使得修改
只影响该模块，⽽不波及其他模块。
信息隐藏 = 隔离变化 = 降低耦合
📖  SW EBO K v4 §1.4 · Encapsulation (inform ation hiding)  |  §1.4 · M odularization

--- PAGE 22 ---
类的职责
类的职责 = 状态（State）+ ⾏为能⼒（Behavioral Capability）
状态（State）
类所持有的数据
描述对象在某⼀时刻的情况
通过字段（ﬁeld）表示
class BankAccount {
    private double balance;  // 状态
    private String owner;    // 状态
}
⾏为能⼒（Behavioral Capability）
类能对外提供的操作
改变状态或查询状态
通过⽅法（method）表示
class BankAccount {
    void deposit(double amount) { ... }
    void withdraw(double amount) { ... }
    double getBalance() { ... }
}
类的接⼝（interface）= 对外承诺的⾏为能⼒；类的实现（implementation）= 内部状态与算法细节。

封装的五种类型（A–E）
类型 隐藏内容 核⼼⼿段
A — 数据类型（ADT） 内部数据表示 访问器/修改器替代 public 字段
B — 内部结构 数据的组织结构 不暴露内部容器/数组
C — 其他对象引⽤ 内部持有哪些对象不直接返回内部对象引⽤
D — 类型信息（LSP） 对象的具体运⾏时类型⾯向接⼝，多态调度
E — 潜在变更 可能变化的实现策略策略模式、依赖注⼊
类型 A–C 处理当前实现细节的封装；类型 D–E 处理未来变化的封装。这五种类型覆盖了⾯向对象封装的完整语义。

类型 A：ADT — 抽象数据类型
ADT 定义的是概念，不是实现。
公开字段（违反封装 A）
class Point {
    public double x;  // 暴露实现：直⻆坐标
    public double y;
}
// 调⽤⽅直接依赖坐标系！
point.x = 3.0;
若改为极坐标实现，所有调⽤⽅都要修改。
ADT 封装（推荐）
class Point {
    private double x, y;
    // 直⻆坐标接⼝
    double getX() { return x; }
    double getY() { return y; }
    // 极坐标接⼝（同⼀  ADT ）
    double getR() {
        return Math.sqrt(x*x + y*y);
    }
    double getTheta() {
        return Math.atan2(y, x);
    }
}

访问器与修改器（Accessor / Mutator）
⽤⽅法替代直接的 public 字段访问：
反模式：直接字段访问
class Person {
    public String name;
    public int age;
}
// 调⽤⽅：
person.age = -5;  // ⽆法验证！
问题：
⽆法添加验证逻辑
字段类型变更破坏调⽤⽅
⽆法懒加载或计算
正确做法：访问器 + 修改器
class Person {
    private String name;
    private int age;
    public int getAge() { return age; }
    public void setAge(int age) {
        if (age < 0 || age > 150)
            throw new IllegalArgumentException();
        this.age = age;
    }
}

类型 B/C：隐藏内部结构与对象引⽤
问题：暴露内部集合（违反 B+C）
class Route {
    public List<Stop> stops;  // 直接暴露！
}
// 调⽤⽅可以任意修改内部状态：
route.stops.add(newStop);    // 绕过业务规则
route.stops.clear();         // 危险！
修复：使⽤ Iterator 或受控接⼝
class Route {
    private List<Stop> stops = new ArrayList<>();
    // 只暴露迭代能⼒
    public Iterator<Stop> getStops() {
        return Collections
            .unmodifiableList(stops)
            .iterator();
    }
    // 受控的修改接⼝
    public void addStop(Stop s) {
        // 可以在这⾥加业务验证
        stops.add(s);
    }
}
Iterator 模式是封装集合内部结构的标准⼿段——调⽤⽅只知道可以遍历，不知道内部是 List 、Set 还是数组。

类型 D：隐藏类型信息（LSP）
调⽤⽅应该依赖接⼝，⽽不需要知道对象的具体类型。
违反封装 D：instanceof 判断
void process(Shape shape) {
    if (shape instanceof Circle) {
        ((Circle) shape).drawCircle();
    } else if (shape instanceof Square) {
        ((Square) shape).drawSquare();
    }
}
问题：每增加⼀种 Shape ，就要修改这段代码。
正确：多态调度
interface Shape {
    void draw();  // 统⼀接⼝
}
class Circle implements Shape {
    public void draw() { /* 画圆  */ }
}
class Square implements Shape {
    public void draw() { /* 画⽅  */ }
}
void process(Shape shape) {
    shape.draw();  // 不知道也不需要知道类型
}

类型 E：封装潜在变更
将可能变化的部分隔离为独⽴模块，其余部分依赖稳定的接⼝。
问题：变化硬编码在类内部
class Sorter {
    void sort(int[] arr) {
        // 直接写死冒泡排序
        // 若要换快速排序，必须修改本类
        bubbleSort(arr);
    }
}
策略模式封装变更
interface SortStrategy {
    void sort(int[] arr);
}
class Sorter {
    private SortStrategy strategy;
    Sorter(SortStrategy s) {
        this.strategy = s;
    }
    void sort(int[] arr) {
        strategy.sort(arr);  // 委托给策略
    }
}
封装类型 E 与**开闭原则（O CP）**直接对应：对扩展开放，对修改关闭。 29

P9 · 为变更⽽封装（Encapsulate W hat Varies）
找到系统中变化的部分，将其封装起来，使变化不影响不变的部分。
识别变化点的三个问题
1. 哪些需求最可能改变？
（算法？数据格式？业务规则？）
2. 哪些部分跨越边界共享？
（多个类都依赖的实现细节）
3. 哪些部分已经变过多次？
（历史修改记录是最好的指示）

变化类型 封装⼿段
算法/策略 策略模式
对象创建⼯⼚⽅法/抽象⼯⼚
对象结构组合模式
跨对象⾏为命令/访问者模式

P10 · 权限最⼩化
M inimize the accessibility of classes and members.
— Eﬀective Java, Joshua Bloch
Java 的四个访问级别
修饰符 可访问范围
private 仅本类内部
（package-private，⽆修饰符）同⼀包内
protected 同⼀包 + ⼦类
public 任何地⽅

为可能有调⽤⽅依赖它。
权限最⼩化的好处：
接⼝更⼩ → 耦合更低
内部实现可以⾃由修改
降低 API 的维护成本
提⾼安全性

P13 · 单⼀职责原则（SRP）
A class should have only one reason to change.
— Robert C. M artin

P14 · SO FA：⽅法级设计原则
SO FA = Short · O ne thing · Few arguments · Abstraction level consistency
— ⾯向⽅法粒度的设计原则（与 SO LID 的类粒度原则互补）
S — Short（⽅法要短）
⽅法体通常 ≤ 20–30 ⾏
过⻓ → 分解为命名清晰的辅助⽅法
O  — O ne thing（只做⼀件事）

F — Few arguments（参数要少）
