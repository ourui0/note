# 实验一 回归测试

按**声明的选做范围**验证实现：本版本声明**只实现选做 3（注释）**，
选做 1（八/十六进制数）与选做 2（指数形式浮点数）**不实现**。

判分规则（本测试套件据此断言）：

* 声明实现的选做 → 必须正常解析并输出语法树；
* 未声明的选做 → 遇到时必须在对应位置报错（不能静默接受）。

**关键实现原则**：不实现选做 1.1/1.2 的正确做法是**不给它们任何特殊规则**，
让基础 token 自然切分，再由语法分析报 B：

| 输入 | 自然切分 | 结果 |
| --- | --- | --- |
| `0123` | `INT(0) INT(123)` | B 类语法错误 |
| `0x3F` | `INT(0) ID(x3F)` | B 类语法错误 |
| `1.05e-4` | `FLOAT(1.05) ID(e) MINUS INT(4)` | B 类语法错误 |
| `1.foo` | `INT(1) DOT ID(foo)` | **合法**，按 `Exp → Exp DOT ID` 出语法树 |

切勿用宽泛正则把 `数字+字母`、`数字+点+字母` 整体吞掉报 A 类错误 —— 那会误杀
`1.foo` 这类文法允许、仅语义无意义的写法（本实验不查语义）。

## 注意点

* **驱动返回码**：`parser.c` 里显式 `return 0`（注释说明 OJ 要求即使有诊断也
  正常退出）。OJ 对错误用例是比对 stdout，因此测试断言诊断内容而非退出码。
* **`parser.c` 与 OJ 构建**：OJ 会对 `parser.y` 跑一次 `yacc` 并输出 `parser.c`。
  当前包里 `parser.c` 比 `parser.y` 新，make 的隐式规则不会触发，因此可正常编译；
  若构建环境让 `parser.c` 变旧，会被 yacc 输出覆盖并导致 `yyparse/yylex/yyerror`
  重复定义，届时需要把驱动改名（例如 `main.c`）——**这一点保持现状，未改动**。
* **行号**：课程样例 4 的期望输出把 `struct Complex x;` 标成第 7 行，但按输入它在
  第 8 行（第 6 行是空行）；样例 3、5 的期望输出与实现完全一致，故按后者为准。


## 官方最终测试用例（Tests_1.zip）

课程官网公开的 `Tests_1.zip` 已下载到本机，可用官方用例做权威比对：

```bash
# 逐字节比较（含说明文字）
python3 /tmp/tests1/exact.py  <parser>
# 按 OJ 口径只比 错误类型+行号
python3 /tmp/tests1/tyline.py <parser>
```

当前结果（只比类型+行号）：**16/20**，必做部分 A-1~A-10、B-1、B-2、C-1、C-2 全部一致；
不一致的 4 个是 D-1、D-2、E1-1、E2-1 —— 它们是选做 1.1（八/十六进制）与
1.2（指数浮点）的合法输入，按"只实现选做 1.3"的声明保持报错，属预期。

**回归教训（重要）**：让 `3.14.15` 报 A 类的规则若写成 `{D}+\.{D}+\.{D}+`（不要求末位是数字），
会把 `1.2.` 也整段吃掉，改变 token 流并导致官方 B-1/B-2 失败（实测 OJ 88→80）。
必须用 `{D}+\.{D}+\.{D}+`（末尾为数字）——已用官方 B-1/B-2 输入与 88 分版逐字节比对确认一致。

官方用例还确认了两个词法归属（本套件已加断言）：

| 输入 | 归属 | 期望 |
| --- | --- | --- |
| `2x`（数字开头的标识符） | **A 类** | `Invalid identifier starting with digit '2x'` |
| `3.14.15`（非法浮点字面量） | **A 类** | `Invalid floating point literal '3.14.15'` |
