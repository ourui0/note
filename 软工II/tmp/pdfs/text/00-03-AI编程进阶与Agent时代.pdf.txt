根因分析：我们真正应该问的问题
真正的问题不是"AI 能不能替代程序员"，⽽是"⼈与 AI 如何⾼效协作"
⼈与 AI 的四种关系（从历史到未来的演进）：
①  ⼈  独  ⽴         ⼯程师独⾃解决所有问题
②  AI 辅  助  ⼈      AI ⼯具提⾼⼯程师⽣产效率       ← 我们现在所处的阶段
③  ⼈  辅  助  AI     ⼯程师为  AI Agent 提供⽅向和审查   ← 正在进⼊
④  AI 独  ⽴         AI ⾃主完成端到端软件⼯程任务     ← 未来（距今还很远）
今天的定论：处于②→③过渡期。
最⾼效的⼯程师 = 能精确指导 AI、能审查 AI 输出、能处理 AI ⽆法处理的边界
 Devin 的案例告诉我们：AI 的宣传往往超前于现实；但趋势的⽅向是真实的

提示词进阶：精准控制 AI 的边界
AI 在项⽬中最常⻅的失误：改动范围失控（你让它修⼀个 bug，它重写了整个⽂件）
5 个控制提示词（来⾃真实使⽤经验）：
1. " 仅修复此问题，不要修改其他代码 "
   → 防⽌  AI 顺⼿ " 优化 " 你不想动的部分
2. " 请使⽤最⼩修改来解决此问题 "
   → 保持代码⻛格⼀致，减少  git diff 噪⾳
3. " 换个思路来解决此问题 "
   → 当前⽅案性能差或逻辑混乱，让  AI 从头重想
4. " 仔细阅读全⽂，检查是否还有其他同类问题 "
   → AI 容易只看局部；这个提示词强制它做全局审查
5. " 请为我梳理当前代码的整体逻辑 "
   → 接⼿陌⽣项⽬时，让  AI 帮你⽣成 " 项⽬导览 "

--- PAGE 8 ---
提示词进阶：代码质量与可维护性
5 个质量提升提示词：
6. " 请提供详细的解释和⾏内代码注释 "
   → ⽣成可维护的代码，⽽不是神秘的⿊盒
7. " ⽣成测试⽤例来验证此更改，
    包含正常路径、边界条件和异常路径 "
   → ⽐  " ⽣成测试 " 更精准，覆盖率更⾼
8. " 增加详细的⽇志输出，⽅便追溯错误 "
   → Debug 时事半功倍
9. " 请简化代码逻辑，去除冗余部分，
    但保持功能完全⼀致 "
   → 加  " 保持功能⼀致 " 是关键约束，防⽌  AI 改变⾏为
10. " 优化代码结构，使其更加模块化，
     每个函数只做⼀件事 "
    → 明确重构⽬标（单⼀职责原则）

跨⽂件理解：处理真实项⽬
场景：拿到⼀个 Java Spring Boot 项⽬，要新增⼀个功能
  错误做法（只看当前⽂件）：
    打开  UserController.java ，问  AI " 帮我加⼀个查询⽤户列表的接⼝ "
    → AI 不知道  UserService 和  UserMapper 已有什么⽅法
    → ⽣成重复代码，或与现有逻辑冲突
  正确做法（ Cursor Ctrl+Enter ，扫描整个项⽬）：
    " 这个项⽬已有哪些⽤户相关的接⼝？
     UserMapper 已实现了哪些查询⽅法？
     我要新增  ' 按⻆⾊查询⽤户列表 ' 接⼝，应该在哪些⽂件⾥做什么修改？ "
    → AI 给出跨⽂件的完整修改⽅案
原则：给 AI 的上下⽂越完整，它的输出越准确——垃圾输⼊，垃圾输出

AI 辅助 Debug：系统化流程
第⼀步：提供完整上下⽂
  " 以下代码在运⾏时报  NullPointerException ，
   错误堆栈是： [ 粘贴完整的  stack trace]
   相关代码是： [ 粘贴出错⽅法  + 调⽤⽅法 ]"
第⼆步：让  AI 分析根因（不要直接让它改代码）
  " 请分析这个  NPE 的根本原因，不要修改代码，先给出分析 "
第三步：确认理解后，再让  AI 修复
  " 你的分析正确，现在⽤最⼩修改修复这个问题，
   只修改  UserService.getUserById() ⽅法 "
第四步：验证修复
  " 为这个修复⽣成  2 个测试⽤例：
   ⼀个正常路径（⽤户存在），⼀个异常路径（⽤户不存在） "
为什么分步骤：直接让 AI "修复 Bug" 往往改动范围太⼤，且你不理解原因

AI 辅助代码审查
场景：收到同学的 PR，⽤ AI 快速找出问题
提示词模板：
" 请审查以下代码，重点检查：
 1. 潜在的安全问题（ SQL 注⼊、 XSS 、权限验证缺失）
 2. 性能问题（ N+1 查询、不必要的循环）
 3. 可维护性问题（⽅法过⻓、命名不清晰）
 4. 边界条件处理（空值、空列表、越界）
 给出每个问题的：位置、严重程度（⾼ / 中 / 低）、修改建议
 不要重写代码，只给出⽂字分析 "
💡  AI 的代码审查是⼈⼯审查的补充，不是替代——安全问题和业务逻辑问题仍需⼈⼯判断

 停下来想⼀想
"AI 能完全替代 Code Review 吗？"
能⼒维度 AI 表现 ⼈⼯优势
语法和拼写错误  ⾮常擅⻓ —
常⻅安全漏洞（SQL i、XSS）  较好 —
性能问题识别  局部可以 需要理解整体架构
业务逻辑正确性  不了解业务 必须由⼈判断
隐式约束（如安全合规）  不了解公司规范必须由⼈判断
需求合理性  只看代码 必须联系产品需求
结论：AI Code Review = ⾃动化 Linter 的升级版——捕获语法/常⻅漏洞⾮常⾼效，但业务正确性和架构决策必须⼈⼯审查

什么是软件⼯程 Agent？
Agent = 能⾃主执⾏多步任务的 AI 系统
传统  AI ⼯具（被动）：
  你输⼊  → AI 输出  → 你执⾏
  （每⼀步都需要⼈来触发）
AI Agent （主动）：
  你描述⽬标  → Agent ⾃主规划步骤  → Agent 调⽤⼯具执⾏
  → Agent 检查结果  → Agent 调整计划  → 直到完成⽬标
  （⼈只需提供⽬标和最终审查）
当前真实能⼒（2025 年实测）：
修复简单 Bug：Agent 已相当可靠
添加单⼀功能：在上下⽂清晰时表现较好
端到端开发完整功能：仍需⼤量⼈⼯指导

--- PAGE 19 ---
让 Agent 理解需求：Spec（规格说明）
最⼤挑战：Agent 执⾏的是你描述的需求，不是你脑⼦⾥真实的需求
  模糊的任务描述（导致  Agent 跑偏）：
    " 帮我实现⽤户注册功能 "
  清晰的  Spec （让  Agent 准确执⾏）：
    " 实现⽤户注册功能，具体要求：
     1. POST /api/auth/register 接⼝
     2. 请求体： { username, password, email }
     3. 密码⽤  BCrypt 加密后存⼊  users 表
     4. username 和  email 不允许重复，重复时返回  409 状态码
     5. 成功返回  { userId, username, message: ' 注册成功 ' }
     6. 只修改  AuthController.java 和  UserMapper.java
     7. 复⽤已有的  UserService ，不要创建新类 "
核⼼：Spec 越精确，Agent 越可靠——这与需求⼯程的原则完全⼀致

降低复杂度：Skill（技能模块化）
问题：复杂项⽬中，Agent 在多个任务之间切换时容易"忘记上下⽂"
解决⽅案：将可复⽤的任务封装成 Skill（技能模块）
项⽬初始化  Skill （⼀次定义，反复使⽤）：
  " 当我说  ' 初始化新  API 接⼝ ' 时，总是：
   1. 在  controller/ 创建  Controller 类（遵循项⽬的命名规范）
   2. 在  service/ 创建对应  Service 接⼝和实现类
   3. 在  mapper/ 创建  Mapper 接⼝
   4. 在  mapper/xml/ 创建  XML ⽂件
   5. 在  entity/ 创建实体类
   6. ⽣成⼀个基础的  GET 接⼝作为⼊⼝ "
代码审查  Skill ：
  " 当我说  ' 审查这段代码 ' 时，总是检查：
   SQL 注⼊⻛险  · NPE ⻛险  · 事务边界  · 命名规范 "

未来的⼈机协作模式
⼈找服务 → 服务找⼈
传统模式（⼈找服务）：
  ⽤户打开  App → 搜索功能  → ⼿动操作  → 完成任务
Agent 模式（服务找⼈）：
  Agent 主动感知⽤户需求
  → 调⽤多个服务完成任务
  → 只在关键决策点询问⽤户
  → 完成后汇报结果
新兴交互范式：
A2UI（AI to UI）：AI 根据任务动态⽣成界⾯（CopilotKit）
Cowork（协同⼯作）：⼈和 AI 在同⼀个⼯作流中实时协作，⽽不是交替轮流
群聊式 Agent：多个 AI Agent 协作（类似企业微信群），分别承担设计/开发/测试⻆⾊
 这些不是遥远的未来——部分已经在⼯具中实现
