# 第07章 第一部分：数据库设计

资料来源：`第07章/第07章_1_数据库设计2026.pdf`

## 一、数据库设计概述

### 1. 数据库设计的含义

广义的数据库设计，是数据库及其应用系统的设计，即设计整个数据库系统（数据库应用系统）。

狭义的数据库设计，是设计数据库本身，即设计数据库的各级模式并建立数据库。好的数据库模式设计与数据库应用系统密不可分。

本课程主要讲授狭义数据库设计涉及的关键技术和方法。

数据库设计的定义：对于一个给定的应用环境，构造优化的数据库逻辑模式和物理结构，并据此建立数据库及其应用系统，使其能够有效存储和管理数据，满足各种用户的应用需求。

用户需求包括：

- 信息管理要求：数据库中应该存储和管理哪些数据对象，也称数据需求。
- 数据操作要求：对数据对象需要进行哪些操作，如查询、增加、删除、修改、统计等，也称处理需求。

数据库设计目标：为用户和各种应用系统提供信息基础设施和高效率运行环境。

高效率运行环境体现为：

- 数据存取效率高。
- 存储空间利用率高。
- 系统运行管理效率高。

### 2. 数据库设计的特点

数据库建设的基本规律：三分技术，七分管理，十二分基础数据。

管理包括：

- 数据库建设项目管理。
- 企业或应用部门的业务管理。

基础数据包括：

- 数据的收集。
- 数据的整理。
- 数据的组织。
- 数据的不断更新。

数据库设计必须把结构设计和行为设计结合起来：

- 结构设计：数据库的数据结构、模式、关系、约束等。
- 行为设计：应用系统中的事务、处理流程、查询、更新、统计等。

传统软件工程偏重行为设计，容易忽视数据语义分析和抽象；早期数据库设计偏重结构设计，容易忽视行为设计对结构设计的影响。因此现代数据库设计应将数据库结构设计与数据处理设计密切结合。

### 3. 数据库设计方法

大型数据库设计是一项涉及多学科的综合性工程，需要以下知识：

- 计算机基础知识。
- 软件工程原理和方法。
- 程序设计方法和技巧。
- 数据库基本知识。
- 数据库设计技术。
- 应用领域知识。

早期数据库设计常用手工试凑法，即手工与经验结合。缺点是：

- 设计质量依赖设计人员经验和水平。
- 缺少科学理论和工程方法支持，质量难以保证。
- 数据库运行一段时间后容易暴露问题，维护代价高。

规范设计法的基本思想是过程迭代和逐步求精。常见方法包括：

- 新奥尔良方法。
- 基于 E-R 模型的数据库设计方法，适用于概念结构设计。
- 3NF 设计方法，适用于关系数据库逻辑结构设计。
- 面向对象的数据库设计方法。
- UML 方法。

### 4. 数据库设计的基本步骤

新奥尔良方法把数据库设计分为六个阶段：

1. 需求分析。
2. 概念结构设计。
3. 逻辑结构设计。
4. 物理结构设计。
5. 数据库实施。
6. 数据库运行和维护。

其中：

- 需求分析和概念设计独立于任何 DBMS。
- 逻辑设计和物理设计与所选 DBMS 密切相关。

参与人员及职责：

- 系统分析人员和数据库设计人员：自始至终参与数据库设计，其水平决定数据库系统质量。
- 数据库管理员和用户代表：主要参加需求分析，以及数据库运行和维护。
- 应用开发人员：包括程序员和操作员，在实施阶段参与，负责编程和准备软硬件环境。

六个阶段的主要任务：

1. 需求分析阶段：充分、准确地了解用户需求，其结果决定后续数据库构建速度和质量。
2. 概念结构设计阶段：对用户需求进行综合、归纳、抽象，形成独立于具体 DBMS 的概念数据模型。
3. 逻辑结构设计阶段：把概念结构转换成某个 DBMS 支持的逻辑数据模型，并优化。
4. 物理结构设计阶段：为逻辑数据结构选择适合应用环境的物理结构，包括存储结构和存取方法。
5. 数据库实施阶段：根据逻辑设计和物理设计结果构建数据库，编写并调试应用程序，组织数据入库并试运行。
6. 数据库运行和维护阶段：试运行后投入正式运行，并在运行中不断评估、调整、修改。

数据库应用系统的设计通常是六个阶段不断反复的过程。数据库设计和数据库中数据处理的设计要紧密结合，在各阶段同时分析、抽象、设计、实现，相互参照和补充。

### 5. 数据库设计过程中的各级模式

数据库设计不同阶段会形成不同层次的模式：

- 需求分析阶段：综合各用户的应用需求。
- 概念设计阶段：形成独立于机器特点和 DBMS 产品的概念模式，通常用 E-R 图表示。
- 逻辑设计阶段：
  - 先将 E-R 图转换为具体数据库产品支持的数据模型，如关系模型，形成数据库逻辑模式。
  - 再根据用户处理要求和安全性考虑，在基本表基础上建立必要视图，形成外模式。
- 物理设计阶段：根据 DBMS 特点和处理需要，进行物理存储安排，建立索引，形成内模式。

## 二、需求分析

### 1. 需求分析的地位

需求分析就是分析用户的要求，是数据库设计的起点。需求分析结果能否准确反映用户实际要求，将直接影响后续各阶段设计，并影响设计结果是否合理、实用。

### 2. 需求分析的任务

需求分析要完成：

- 详细调查现实世界中要处理的对象，如组织、部门、企业等。
- 充分了解原系统，包括手工系统或计算机系统的工作概况。
- 明确用户的各种需求。
- 在此基础上确定新系统功能。
- 充分考虑今后可能的扩充和改变。

调查重点是“数据”和“处理”，获得用户对数据库的要求：

- 信息要求：用户需要从数据库中获得的信息内容与性质。由信息要求可以导出数据要求，即数据库中需要存储哪些数据。
- 处理要求：用户要完成的处理功能，以及对处理性能的要求。
- 安全性与完整性要求。

确定用户最终需求的难点：

- 用户缺少计算机知识，不能准确表达需求，而且需求常变化。
- 设计人员缺少用户专业知识，不容易理解用户真正需求，甚至可能误解。

解决方法：设计人员必须不断深入地与用户交流，逐步确定用户实际需求。

### 3. 需求分析的方法

需求分析过程：

1. 调查：调查清楚用户实际需求，并进行初步分析。
2. 确认：与用户达成共识。
3. 表达并再次确认：分析和表达这些需求，并交给用户确认。

调查用户需求的步骤：

1. 调查组织机构情况：了解部门组成、职责等，为分析信息流程做准备。
2. 调查各部门业务活动情况：了解各部门输入和使用什么数据，如何加工，输出什么信息，输出到哪些部门，输出格式是什么等。
3. 在熟悉业务活动基础上协助用户明确新系统要求，包括信息要求、处理要求、安全性与完整性要求等。
4. 确定新系统边界：分析哪些功能由计算机完成或将来准备由计算机完成，哪些活动由人工完成。

常用调查方法：

- 跟班作业：亲自参加业务工作，了解业务活动。
- 开调查会：与用户座谈，了解业务活动和用户需求。
- 请专人介绍。
- 询问：针对调查中的具体问题找专人询问。
- 设计调查表请用户填写。
- 查阅记录：查阅与原系统有关的数据记录。

进一步分析和表达用户需求时，常用结构化分析方法（SA 方法）。SA 方法从最上层系统组织机构入手，采用自顶向下、逐层分解的方式分析系统。

需求分析报告必须提交给用户，征得用户认可。

需求分析阶段的设计结果：

- 数据字典。
- 用户需求规格说明书。

它们是下一阶段概念设计的基础和输入。

### 4. 数据字典

数据字典是关于数据库中数据的描述，即元数据，也称基础数据，不是数据本身。

数据字典的特点：

- 在需求分析阶段建立。
- 在数据库设计过程中不断修改、充实、完善。
- 是详细数据收集和数据分析得到的主要结果。
- 是下一阶段设计的基础。

注意：这里的数据字典与关系 DBMS 中系统数据字典既有区别也有联系。需求分析中的数据字典用于描述应用数据需求；DBMS 中的数据字典通常用于记录数据库对象定义和系统元数据。

数据字典内容：

- 数据项。
- 数据结构。
- 数据流。
- 数据存储。
- 处理过程。

数据项是数据的最小组成单位；若干数据项可以组成一个数据结构；数据字典通过数据项和数据结构的定义，描述数据流、数据存储的逻辑内容。

#### 数据项

数据项是不可再分的数据单位。

数据项描述：

```text
数据项描述 = {
  数据项名,
  数据项含义说明,
  别名,
  数据类型,
  长度,
  取值范围,
  取值含义,
  与其他数据项的逻辑关系,
  数据项之间的联系
}
```

其中“取值范围”和“与其他数据项的逻辑关系”定义了数据完整性约束条件，是设计数据检验功能的依据。可以用关系规范化理论为指导，用数据依赖概念分析和表示数据项之间的联系。

#### 数据结构

数据结构反映数据之间的组合关系。一个数据结构可以由若干数据项组成，也可以由若干数据结构组成，或由数据项和数据结构混合组成。

数据结构描述：

```text
数据结构描述 = {
  数据结构名,
  含义说明,
  组成: {数据项或数据结构}
}
```

#### 数据流

数据流是数据结构在系统内传输的路径。

数据流描述：

```text
数据流描述 = {
  数据流名,
  说明,
  数据流来源,
  数据流去向,
  组成: {数据结构},
  平均流量,
  高峰期流量
}
```

说明：

- 数据流来源：该数据流来自哪个过程。
- 数据流去向：该数据流将到哪个过程。
- 平均流量：单位时间内传输次数，如每天、每周、每月。
- 高峰期流量：高峰时期的数据流量。

#### 数据存储

数据存储是数据结构停留或保存的地方，也是数据流来源和去向之一。

数据存储描述：

```text
数据存储描述 = {
  数据存储名,
  说明,
  编号,
  输入的数据流,
  输出的数据流,
  组成: {数据结构},
  数据量,
  存取频度,
  存取方式
}
```

说明：

- 存取频度：每小时、每天或每周存取次数，每次存取的数据量等。
- 存取方法：批处理或联机处理；检索或更新；顺序检索或随机检索。
- 输入的数据流：数据来源。
- 输出的数据流：数据去向。

#### 处理过程

处理过程的具体处理逻辑一般用判定表或判定树描述。数据字典中只需要描述处理过程的说明性信息。

处理过程描述：

```text
处理过程描述 = {
  处理过程名,
  说明,
  输入: {数据流},
  输出: {数据流},
  处理: {简要说明}
}
```

简要说明包括：

- 功能要求：该处理过程做什么。
- 处理要求：处理频度、单位时间事务量、数据量、响应时间要求等。

处理要求是后面物理设计的输入和性能评价标准。

#### 例：判定表与判定树

讲义用“航空行李托运费的计算”作为处理逻辑描述的例子。

判定表用表格描述处理逻辑，分为四部分：

- 左上：基本条件项。
- 右上：条件判定。
- 左下：基本动作项。
- 右下：操作动作。

判定树用树形结构描述条件分支和对应动作。

### 5. 需求分析小结

把需求收集和分析作为数据库设计第一阶段十分重要。

需求分析结果包括：

- 数据字典。
- 用户需求规格说明书。

这些基础数据和用户需求规格说明书，是下一步概念设计的基础和输入。

应强调两点：

- 设计人员应充分考虑可能的扩充和改变，使设计易于更改，系统易于扩充。
- 必须强调用户参与。

## 三、概念结构设计

### 1. 概念模型

将需求分析得到的用户需求抽象为信息结构，即概念模型的过程，就是概念结构设计。

概念模型特点：

- 能真实、充分地反映现实世界，是现实世界的真实模型。
- 易于理解，便于与不熟悉计算机的用户交换意见。
- 易于更改，当应用环境和应用要求变化时，容易修改和扩充。
- 易于向关系、网状、层次等各种数据模型转换。

描述概念模型的工具：

- E-R 模型。
- EER 模型。

### 2. 概念结构设计的方法

概念结构设计方法包括：

- 自顶向下。
- 自底向上。
- 逐步扩张。
- 混合策略。

自顶向下：先定义全局概念结构框架，再逐步细化。

自底向上：先定义各局部应用的概念结构，再集成得到全局概念结构。

逐步扩张：先定义最重要的核心概念结构，再向外扩充，以滚雪球方式逐步生成其他概念结构，直到总体概念结构。类似软件工程中的螺旋模型。

混合策略：结合自顶向下和自底向上。用自顶向下策略设计全局概念结构框架，再以它为骨架集成自底向上设计的各局部概念结构。

常用策略：

- 自顶向下进行需求分析。
- 自底向上设计概念结构。

自底向上设计概念结构的步骤：

1. 抽象数据并设计局部视图。
2. 集成局部视图，得到全局概念结构。

整个过程以需求分析、数据流图 DFD、数据字典 DD 为输入，经过数据抽象和局部视图设计得到分 E-R 图，再进行视图集成得到总 E-R 图，并反复征求用户意见直到满意。

### 3. E-R 模型设计选择

E-R 模型设计中常见选择包括：

- 实体还是属性。
- 实体还是联系。
- 二元联系还是多元联系。
- 属性依附于实体还是联系。

#### 实体与属性的划分原则

为了简化 E-R 图，现实世界中能作为属性对待的事物，应尽量作为属性对待。

两个准则：

1. 作为属性，不能再具有需要描述的性质。属性必须是不可分的数据项，不能包含其他属性。
2. 属性不能与其他实体具有联系。E-R 图中表示的联系是实体之间的联系。

说明：在扩展 E-R 模型中，属性可以不必遵循原子性。

#### 例1：职工与职称

职工是实体，职工号、姓名、年龄是职工的属性。

- 如果职称没有与工资、福利挂钩，也没有进一步需要描述的特性，根据准则 1，职称可以作为职工实体的属性。
- 如果不同职称有不同工资、住房标准和附加福利，则职称作为实体更恰当。

#### 例2：病人与病房

在医院中：

- 如果一个病人只能住在一个病房，病房号可以作为病人实体的属性。
- 如果病房还要与医生实体发生联系，例如一个医生负责几个病房的病人的医疗工作，则根据准则 2，病房应作为实体。

#### 例3：货物与仓库

- 如果一种货物只存放在一个仓库，可以把仓库号作为描述货物存放地点的属性。
- 如果一种货物可以存放在多个仓库中，或仓库本身还要用面积作为属性，或仓库与职工发生管理联系，则应把仓库作为实体。

#### 例7.1：销售管理子系统 E-R 图设计

销售管理子系统主要功能：

- 处理顾客和销售员送来的订单。
- 工厂根据订货安排生产。
- 交出货物同时开出发票。
- 收到顾客付款后，根据发票存根和信贷情况进行应收款处理。

根据需求分析和数据字典，遵循实体与属性划分准则进行调整：

1. 每张订单由订单号、若干头信息和订单细节组成。订单细节由订货零件号、数量等描述。按照准则 2，订单细节不能作为订单属性，而应上升为实体。一张订单可订若干产品，因此订单与订单细节之间是 1:n 联系。
2. 原订单和产品的联系实际上是订单细节和产品的联系。每条订单细节对应一个产品描述，订单处理时从中获得当前单价、产品重量等信息。
3. 工厂对大宗订货给予优惠。每种产品都规定不同订货数量的折扣，因此应增加“折扣规则”实体存放这些信息，而不应放在产品实体中。

该销售管理子系统中各实体属性：

- 顾客：`{顾客号，顾客名，地址，电话，信贷状况，账目余额}`
- 订单：`{订单号，顾客号，订货项数，订货日期，交货日期，工种号，生产地点}`
- 订单细则：`{订单号，细则号，零件号，订货数，金额}`
- 应收账款：`{顾客号，订单号，发票号，应收金额，支付日期，支付金额，当前余额，货款限额}`
- 产品：`{产品号，产品名，单价，重量}`
- 折扣规则：`{产品号，订货量，折扣}`

#### 实体还是联系

实体：可以独立存在的持久对象，可以是有形对象，如人、物体，也可以是无形或抽象对象，如组织机构、地理位置。

联系：因某种需要或某件事情发生而产生的信息，通常与现实世界中的多个对象有关。

有些现实世界中的事件也可抽象为实体。

例：商品销售。

- 如果是实体店商品零售，可以用商品、顾客、销售商之间的二元或多元联系表示。
- 如果是大宗商品或网络销售，买卖双方通常签订销售合同或订单，则可将合同或订单抽象为实体，再通过订单实体与顾客、商品、销售商等实体之间的若干二元联系建立供销关系。

#### 二元联系还是多元联系

选择依据：联系语义描述需要，以及因此涉及的实体个数。

三元或多元联系中，如果用户只需要使用实体之间的两两联系，且不会出现二义性或歧义性，可以考虑用若干二元联系实现。

也可以将联系抽象为实体，再在该“联系实体”和其他实体之间建立若干二元联系。

#### 属性的依附对象

属性可以依附于实体，也可以依附于联系。

实体属性：

- 是实体的内在特征。
- 不会因某些联系的出现而产生、改变或消亡。

联系属性：

- 用于描述因联系发生而需要记录和存储的信息。
- 其值随联系产生而出现，也随联系消亡而消亡。

### 4. E-R 图的集成

E-R 图集成一般分两步：

1. 合并：解决各分 E-R 图之间的冲突，将分 E-R 图合并成初步 E-R 图。
2. 修改和重构：消除不必要冗余，生成基本 E-R 图。

#### 合并 E-R 图

各局部应用面向的问题不同，各子系统 E-R 图之间会存在不一致，称为冲突。

子系统 E-R 图冲突主要有三类：

- 属性冲突。
- 命名冲突。
- 结构冲突。

#### 属性冲突

属性定义一般遵循“同名同义、异名异义”原则。

属性冲突包括：

- 属性域冲突：属性值的类型、取值范围或取值集合不同。
- 属性取值单位冲突。

例：属性域冲突。

- 零件号：有的部门定义为整数，有的定义为字符型。
- 年龄：某些部门用出生日期表示，另一些部门用整数表示。

例：属性取值单位冲突。

- 零件重量：有的以公斤为单位，有的以斤为单位，有的以克为单位。

解决方法：各部门讨论协商，共同制定解决方案。

#### 命名冲突

模型对象命名一般也遵循“同名同义、异名异义”原则。

命名冲突包括：

- 同名异义：不同意义的对象在不同局部应用中具有相同名字。
- 异名同义或一义多名：同一意义的对象在不同局部应用中具有不同名字。

例：科研项目在财务科称为项目，在科研处称为课题，在生产管理处称为工程。

命名冲突可能发生在实体、联系层面，也可能发生在属性层面。

解决方法：通过讨论、协商等行政手段解决，通常是换名或统一命名。

#### 结构冲突

结构冲突主要包括：

1. 同一对象在不同应用中具有不同抽象。例：职工在某局部应用中作为实体，在另一局部应用中作为属性。解决方法是把属性变换为实体，或把实体变换为属性，使同一对象具有相同抽象，同时仍遵循实体与属性划分原则。
2. 同一实体在不同子系统 E-R 图中所包含属性个数和属性排列次序不完全相同。解决方法是使该实体属性取各子系统 E-R 图中属性的并集，再适当调整属性次序。
3. 实体间联系在不同 E-R 图中为不同类型。例：实体 E1 与 E2 在一个 E-R 图中是 m:n 联系，在另一个 E-R 图中是 1:n 联系。解决方法是根据应用语义综合或调整实体联系类型。

例：结构冲突集成。

- 一个 E-R 图中，零件与产品之间存在 m:n 联系“构成”。
- 另一个 E-R 图中，产品、零件、供应商三者之间存在 m:n 联系“供应”。
- 合并时需要根据语义把两个局部 E-R 图集成为统一模型。

#### E-R 图的修改和重构

目标：消除不必要冗余，设计基本 E-R 图。

冗余数据：可由基本数据导出的数据。

冗余联系：可由其他联系导出的联系。

消除冗余主要采用分析方法：以数据字典和数据流图为依据，根据数据字典中数据项之间逻辑关系的说明消除冗余。

例：消除冗余。

- 若 `Q3 = Q1 × Q2`，则 Q3 可由 Q1 和 Q2 推出，是冗余数据。
- 若 `Q4 = ΣQ5`，则 Q4 可由 Q5 汇总推出，是冗余数据。
- 如果 Q3 被消去，由 Q3 引起的产品与材料之间 m:n 冗余联系也应消去。
- 但并非所有冗余数据和冗余联系都必须消除，有时为了提高效率，需要以冗余信息为代价。

#### 用规范化理论消除冗余

步骤：

1. 确定分 E-R 图实体之间的数据依赖。实体之间 1:1、1:n、m:n 联系可以用实体码之间的函数依赖表示，形成函数依赖集 `FL`。
2. 求 `FL` 的最小覆盖 `GL`。
3. 计算差集 `D = FL - GL`。
4. 逐一考察 `D` 中的函数依赖，判断是否为冗余联系；若是，则删除。

例：函数依赖表示联系。

- 部门和职工之间 1:n 联系“属于”可表示为：`职工号 → 部门号`。
- 职工和产品之间 m:n 联系“生产”可表示为：`(职工号, 产品号) → 工作天数`。

注意：规范化理论受“泛关系假设”限制，使用时要注意：

- 冗余联系一定在 `D = FL - GL` 中，但 `D` 中的联系不一定都是冗余的。
- 当实体之间存在多种联系时，要在形式上区分这些联系。

例：部门和职工之间另一个 1:1 联系“负责”可表示为：

```text
负责人.职工号 → 部门号
部门号 → 负责人.职工号
```

#### 例7.2：某工厂管理信息系统的视图集成

讲义将以下分 E-R 图进行集成：

- 工厂物资管理 E-R 图。
- 劳动人事管理分 E-R 图。
- 销售管理子系统 E-R 图。

集成得到某工厂管理信息系统的基本 E-R 图。

集成中的处理：

- “项目”和“产品”是异名同义。某个项目实质上指某个产品的生产，因此统一使用“产品”作为实体名。
- 库存管理中职工与仓库的工作关系，已包含在劳动人事管理中部门与职工之间的联系之中，所以可以取消。
- 职工之间领导与被领导关系，可由部门与职工（经理）之间的领导关系、部门与职工之间的从属关系导出，所以也可以取消。

## 四、逻辑结构设计

### 1. 逻辑结构设计的任务

逻辑结构设计的任务：把概念结构设计阶段得到的基本 E-R 图转换为与所选 DBMS 支持的数据模型相符合的逻辑结构。

转换内容：

- E-R 图由实体集、实体属性、实体集之间联系三个要素组成。
- 关系模型的逻辑结构是一组关系模式的集合。
- 将 E-R 图转换为关系模型，需要完成：
  - 转换原则：把实体集、实体属性和实体集之间联系转化为关系模式。
  - 模型优化。
  - 设计用户子模式。

### 2. E-R 图转换为关系模型的原则

#### 规则1：实体集转换

一个实体集转换为一个关系模式。

- 关系属性：实体的属性，包括单值属性和组合属性。
- 关系码：实体的标识符。

#### 规则2：多值属性转换

每一个多值属性都单独转换为一个关系。

- 关系属性：实体集的主标识符、多值属性。
- 关系码：实体集的主标识符和多值属性联合组成。

#### 规则3：1:1 联系转换

一个 1:1 联系可以转换为独立关系模式，也可以与任意一端对应的关系模式合并。

转换为独立关系模式时：

- 关系属性：与该联系相连的各实体的码，以及联系本身的属性。
- 候选码：每个实体的码均是该关系的候选码。

与某一端实体关系模式合并时：

- 合并后属性：加入对应关系的码和联系本身的属性。
- 合并后关系码：不变。

#### 规则4：1:n 联系转换

一个 1:n 联系可以转换为独立关系模式，也可以与 n 端对应的关系模式合并。

转换为独立关系模式时：

- 关系属性：与该联系相连的各实体的码，以及联系本身的属性。
- 关系码：n 端实体的码。

与 n 端对应关系模式合并时：

- 合并后属性：在 n 端关系中加入 1 端关系的码和联系本身的属性。
- 合并后关系码：不变。
- 优点：减少系统中的关系个数。

#### 规则5：m:n 联系转换

一个 m:n 联系转换为一个关系模式。

- 关系属性：与该联系相连的各实体的码，以及联系本身的属性。
- 关系码：各实体码的组合。

例：“选修”联系是 m:n 联系，可转换为：

```text
选修（学号，课程号，成绩）
```

其中学号与课程号为组合码。

#### 规则6：多元联系转换

三个或三个以上实体间的多元联系转换为一个关系模式。

- 关系属性：与该多元联系相连的各实体的码，以及联系本身的属性。
- 关系码：各实体码的组合。

#### 规则7：单个实体集内部的联系转换

单个实体集内部的联系向关系转换时，可参照二元联系转换规则。

#### 规则8：ISA 联系转换

ISA 联系也需要转换为关系模式。讲义在此处只列出规则名称，未展开具体转换细节。

#### 具有相同码的关系模式合并

具有相同码的关系模式可以合并。

目的：减少系统中的关系个数。

合并方法：

1. 将其中一个关系模式的全部属性加入另一个关系模式。
2. 去掉同义属性，同义属性可能同名也可能不同名。
3. 适当调整属性次序。

### 3. E-R 图向关系模型转换示例

某工厂管理信息系统基本 E-R 图可转换为如下关系模式：

- 部门（部门号，部门名，经理的职工号，...）
- 职工（职工号，部门号，职工名，职务，...）
- 产品（产品号，产品名，产品组长的职工号，...）
- 供应商（供应商号，姓名，...）
- 零件（零件号，零件名，...）
- 参加（职工号，产品号，工作天数，...）
- 供应（产品号，供应商号，零件号，供应量）

### 4. 数据模型的优化

数据库逻辑设计结果不是唯一的。得到初步数据模型后，应适当修改和调整数据模型结构，以提高数据库应用系统性能，这就是数据模型优化。

关系数据模型优化通常以规范化理论为指导。

模型优化任务：

- 关系规范化设计。
- 冗余函数依赖检查。
- 逆规范化。
- 关系模式分解，包括水平分解和垂直分解。

关系规范化设计：

- 按需求分析阶段得到的语义，分别写出每个关系模式内部属性之间的数据依赖。
- 根据数据依赖理论分析各关系模式，考察是否存在部分函数依赖、传递函数依赖、多值依赖等，确定各关系模式属于第几范式，并按要求开展规范化设计。

不同关系之间冗余函数依赖检查：

- 按需求分析阶段得到的语义，分别写出不同关系模式属性之间的数据依赖。
- 对各关系模式之间的数据依赖进行极小化处理，消除冗余联系。

还要按照需求分析阶段得到的各种应用对数据处理的要求，分析这些模式对应用环境是否合适，确定是否要合并或分解。

注意：并不是规范化程度越高越优。

- 当查询经常涉及两个或多个关系模式的属性时，系统必须经常连接，连接代价高。
- 在这种情况下，第二范式甚至第一范式可能是合适的。
- 非 BCNF 关系模式虽然可能存在更新异常，但如果实际应用中只查询不更新，就不会产生实际影响。
- 对具体应用而言，规范化到什么程度，需要权衡响应时间和潜在问题。

### 5. 关系模式分解

为了提高数据操作效率和存储空间利用率，可对关系模式进行必要分解。

常用分解方法：

- 水平分解。
- 垂直分解。

#### 水平分解

水平分解是把一个基本关系的元组集合划分为若干子集合，每个子集合定义为一个子关系，以提高系统效率。

分解方法：

- 对符合“80/20 原则”的关系，把经常被使用的数据（约 20%）水平分解出来，形成一个子关系。
- 水平分解为若干子关系，使每个事务存取的数据对应一个子关系。

#### 垂直分解

垂直分解是把关系模式 R 的属性集划分为若干子集合，形成若干子关系模式。

垂直分解原则：

- 经常在一起使用的属性从关系 R 中分解出来，形成一个子关系模式。

优点：

- 可以提高某些事务效率。

缺点：

- 可能使另一些事务必须执行连接操作，从而降低效率。

适用范围：

- 取决于分解后关系 R 上所有事务的总效率是否提高。

方法：

- 简单情况：直观分解。
- 复杂情况：使用模式分解算法。

垂直分解必须不损失关系模式语义，即保持无损连接性和保持函数依赖。

### 6. 设计用户子模式

定义数据库模式主要从系统时间效率、空间效率、易维护等角度出发。

定义用户外模式时更注重用户习惯和方便，主要包括：

1. 使用更符合用户习惯的别名。
2. 针对不同级别用户定义不同视图，以保证系统安全性。
3. 简化用户对系统的使用。

使用别名的原因：合并各分 E-R 图时，为消除命名冲突，需要使数据库系统中同一关系和属性具有唯一名字。但在用户视图中，可以用视图机制重新定义某些属性名，使其符合用户习惯。

例：产品关系上的安全视图。

假设有关系模式：

```text
产品（产品号，产品名，规格，单价，生产车间，生产负责人，产品成本，产品合格率，质量等级）
```

可建立两个视图：

```text
产品1（产品号，产品名，规格，单价）
```

用于一般顾客。

```text
产品2（产品号，产品名，规格，单价，车间，生产负责人）
```

用于产品销售部门。

简化用户使用：如果某些局部应用经常使用复杂查询，可将复杂查询定义为视图，方便用户使用。

### 7. 数据库管理系统适应性转换

一般的数据模型还需要向特定 DBMS 规定的模型转换。

转换主要依据所选 DBMS 的功能和限制，没有通用规则。

对关系模型来说，这类转换通常比较简单。

## 五、物理结构设计

### 1. 数据库物理设计

数据库在物理设备上的存储结构与存取方法称为数据库物理结构，它依赖于选定的 DBMS。

为给定逻辑数据模型选取最适合应用要求的物理结构的过程，就是数据库物理设计。

物理设计步骤：

1. 确定数据库物理结构，在关系数据库中主要指存取方法和存储结构。
2. 对物理结构进行评价，重点评价时间效率和空间效率。

如果评价结果满足原设计要求，则进入物理实施阶段；否则需重新设计或修改物理结构，有时甚至要返回逻辑设计阶段修改数据模型。

物理设计内容：

- 数据库物理设计的内容与方法。
- 关系模式存取方法选择。
- 确定数据库的存储结构。
- 评价物理结构。

### 2. 物理设计的准备工作和参数

准备工作：

- 充分了解应用环境，详细分析要运行的事务，以获得选择物理数据库设计所需参数。
- 充分了解所用关系 DBMS 的内部特征，特别是系统提供的存取方法和存储结构。

关系数据库物理设计内容：

- 为关系模式选择存取方法。
- 设计关系、索引等数据库文件的物理存储结构。

物理设计所需参数：

数据库查询事务：

- 查询的关系。
- 查询条件涉及的属性。
- 连接条件涉及的属性。
- 查询的投影属性。

数据库更新事务：

- 被更新的关系。
- 每个关系上更新操作条件涉及的属性。
- 修改操作要改变的属性值。

还要掌握每个事务在各关系上的运行频率和性能要求。

### 3. 关系模式存取方法选择

数据库系统是多用户共享系统。对同一个关系可能要建立多条存取路径，以满足多用户多种应用要求。

物理结构设计任务之一：根据关系 DBMS 支持的存取方法确定选择哪些存取方法。

常用存取方法：

- B+ 树索引存取方法。
- Hash 索引存取方法。
- 聚簇存取方法。

#### B+ 树索引存取方法

选择索引存取方法的主要内容：

- 对哪些属性列建立索引。
- 对哪些属性列建立组合索引。
- 对哪些索引设计为唯一索引。

一般规则：

- 如果一个或一组属性经常在查询条件中出现，考虑建立索引或组合索引。
- 如果一个属性经常作为最大值、最小值等聚集函数参数，考虑建立索引。
- 如果一个或一组属性经常在连接操作的连接条件中出现，考虑建立索引或组合索引。

注意：一个关系上索引过多会带来额外开销，包括维护索引和查找索引的开销。

#### Hash 存取方法

选择 Hash 存取方法的规则：

如果一个关系的属性主要出现在等值连接条件中，或主要出现在等值比较选择条件中，并且满足以下条件之一，可考虑 Hash 存取：

- 该关系大小可预知且不变。
- 该关系大小动态改变，但所选 DBMS 提供动态 Hash 存取方法。

#### 聚簇存取方法

聚簇：为了提高某个属性或属性组的查询速度，把这些属性（聚簇码）上具有相同值的元组集中存放在连续物理块中。

聚簇码：用于聚簇的属性或属性组，也称 cluster key。

用途：显著提高按聚簇属性查询的效率。

例：按系查询学生。

假设学生关系按所在系建有索引，现在要查询信息系所有学生名单。

- 如果计算机系 500 名学生分布在 500 个不同物理块上，至少要执行 500 次 I/O。
- 如果将同一系学生元组集中存放，则每读一个物理块可得到多个满足条件的元组，显著减少磁盘访问次数。

聚簇适用范围：

- 单个关系独立聚簇。
- 经常进行连接操作的多个关系组合聚簇。

多个关系组合聚簇：把多个连接的元组按连接属性值聚集存放，实现多个关系的“预连接”，提高连接效率。

选择聚簇存储方法，就是确定建立多少个聚簇、每个聚簇包含哪些关系。

限制：

- 一个数据库可以建立多个聚簇。
- 一个关系只能加入一个聚簇。

候选聚簇设计：

- 常在一起进行连接操作的关系可建立组合聚簇。
- 如果一个关系的一组属性经常出现在相等比较条件中，该单个关系可建立聚簇。
- 如果一个关系的一个或一组属性值重复率很高，该单个关系可建立聚簇。

检查候选聚簇并取消不必要关系：

- 删除经常进行全表扫描的关系。
- 删除更新操作远多于连接操作的关系。
- 删除重复出现的关系。
- 当一个关系同时加入多个聚簇时，必须从多个聚簇方案以及不建立聚簇方案中选择总代价最小的较优方案。

聚簇的局限性：

- 只能提高某些特定应用性能。
- 建立和维护聚簇开销很大。
- 对已有关系建立聚簇会导致元组物理存储位置移动，并使原有索引无效，必须重建。
- 当元组聚簇码改变时，元组存储位置也要改变。

适合使用聚簇的场景：

- 通过聚簇码访问或连接是该关系的主要应用。
- 与聚簇码无关的其他访问很少或是次要的。
- SQL 中包含与聚簇码有关的 `ORDER BY`、`GROUP BY`、`UNION`、`DISTINCT` 等子句或短语时，使用聚簇特别有利，可省去或简化排序操作。

### 4. 确定数据库存储结构

确定数据库物理结构主要指确定数据存放位置和存储结构，包括：

- 关系的存储安排和结构。
- 索引的存储安排和结构。
- 聚簇的存储安排和结构。
- 日志的存储安排和结构。
- 备份的存储安排和结构。
- 系统配置。

影响因素：

- 硬件环境。
- 应用需求。
- 存取时间。
- 存储空间利用率。
- 维护代价。

存取时间、存储空间利用率、维护代价常相互矛盾，必须权衡，选择折中方案。

#### 确定数据存放位置

基本原则：

- 根据应用情况，将易变部分与稳定部分分开存放。
- 将经常存取部分与存取频率较低部分分开存放。

例：

- 可将较大的表分别放在两个磁盘上，以加快存取速度，在多用户环境中特别有效。
- 可将日志文件与数据库对象（表、索引等）放在不同磁盘，以改进系统性能。

#### 确定系统配置

DBMS 通常提供一些存储分配参数，例如：

- 同时使用数据库的用户数。
- 同时打开的数据库对象数。
- 内存分配参数。
- 缓冲区分配参数，如缓冲区长度、个数。
- 存储分配参数。
- 物理块大小。
- 物理块装填因子。
- 时间片大小。
- 数据库大小。
- 锁的数目。

系统通常为这些变量赋予合理默认值。物理设计时需要根据应用环境确定参数值，使系统性能较优。物理设计阶段对系统配置变量的调整只是初步的，后续还要根据实际运行情况继续调整。

### 5. 评价物理结构

对物理设计中产生的多种方案进行评价，从中选择较优方案作为数据库物理结构。

评价方法：

- 定量估算各种方案的存储空间。
- 定量估算各种方案的存取时间。
- 定量估算各种方案的维护代价。
- 对估算结果进行权衡、比较，选出较优且合理的物理结构。

## 六、数据库实施和维护

### 1. 实施和维护内容

数据库实施和维护包括：

- 数据载入和应用程序调试。
- 数据库试运行。
- 数据库运行和维护。

运行和维护包括：

- 转储与恢复。
- 安全性和完整性控制。
- 数据库性能监督、分析和改造。
- 数据库重组织和重构造。

### 2. 数据载入

数据库结构建立后，即可向数据库装载数据。组织数据入库是数据库实施阶段最主要的工作。

数据装载方法：

- 人工方法。
- 计算机辅助数据入库。

### 3. 应用程序调试

数据库应用程序设计应与数据设计并行进行。

组织数据入库的同时，还要调试应用程序。

应用程序设计、编码、调试的方法和步骤属于软件工程课程内容，讲义不展开。

### 4. 数据库试运行

应用程序调试完成，并已有一小部分数据入库后，即可开始数据库系统联合调试，也称数据库试运行。

主要工作：

- 功能测试：实际运行应用程序，执行对数据库的各种操作，测试应用程序功能。
- 性能测试：测量系统性能指标，分析是否符合设计目标。

数据库性能指标测量：

- 物理设计阶段估算时间、空间指标时作了简化和假设，结果较粗糙。
- 试运行要实际测量系统各类性能指标，不只是时间和空间指标。
- 若结果不符合设计目标，需要返回物理设计阶段调整物理结构和参数；有时甚至需要返回逻辑设计阶段调整逻辑结构。

数据库试运行注意事项：

1. 数据分期入库。
2. 做好数据库转储和恢复。

数据分期入库原因：

- 重新设计物理结构甚至逻辑结构会导致数据重新入库。
- 数据入库工作量很大，因此可先输入小批量数据供先期联合调试使用。
- 待试运行基本合格后再输入大批量数据。
- 逐步增加数据量，逐步完成运行评价。

转储和恢复原因：

- 试运行阶段系统不稳定，软硬件故障随时可能发生。
- 操作人员对新系统不熟悉，误操作不可避免。
- 必须做好转储和恢复，尽量减少对数据库的破坏。

### 5. 数据库运行和维护

数据库运行阶段，经常性维护主要由 DBA 完成，包括：

- 数据库转储和恢复。
- 数据库安全性、完整性控制。
- 数据库性能监督、分析和改进。
- 数据库重组织与重构造。

#### 数据库转储和恢复

DBA 要针对不同应用要求制定不同转储计划，定期备份数据库和日志文件。

一旦发生介质故障，可利用数据库备份和日志文件备份，尽快将数据库恢复到某种一致性状态。

#### 数据库安全性和完整性控制

初始定义：

- DBA 根据用户实际需要授予不同操作权限。
- 根据应用环境定义不同完整性约束条件。

修改定义：

- 当应用环境变化，安全性要求也会变化，DBA 需要根据实际情况修改安全性控制。
- 应用环境变化也会导致完整性约束条件变化，DBA 需要不断修正，以满足用户要求。

#### 数据库性能监督、分析和改进

数据库运行过程中，DBA 必须监督系统运行，分析监测数据，寻找改进性能的方法。

主要工作：

- 利用监测工具获取系统运行过程中的性能参数值。
- 分析这些数据，判断系统是否处于最佳运行状态。
- 若不是，则调整某些参数，进一步改进数据库性能。

#### 数据库重组织

重组织原因：

- 数据库运行一段时间后，由于记录不断增、删、改，物理存储状况变坏。
- 这会降低存储空间利用率和数据存取效率，使数据库性能下降。

重组织形式：

- 全部重组织。
- 部分重组织，如只对频繁增删的表进行重组织。

重组织目标：提高系统性能。

重组织工作：

- 按原设计要求重新安排存储位置。
- 回收垃圾。
- 减少指针链。

注意：数据库重组织不会改变原设计的数据逻辑结构和物理结构。

DBMS 通常提供重组织数据库的实用程序，帮助 DBA 重新组织数据库。

#### 数据库重构造

重构造原因：

- 数据库应用环境发生变化，会导致实体及实体间联系变化，使原数据库设计不能很好满足新需求。

常见变化：

- 增加新的应用或新的实体。
- 取消某些已有应用。
- 改变某些已有应用。

重构造主要工作：

- 根据新环境调整数据库模式和内模式。
- 增加或删除某些数据项。
- 改变数据项类型。
- 增加或删除某个表。
- 改变数据库容量。
- 增加或删除某些索引。

重构造程度是有限的。如果应用变化太大，无法通过重构数据库满足新需求，或重构代价太大，则说明现有数据库应用系统生命周期已经结束，应重新设计新的数据库应用系统。

## 七、全部例子汇总

1. 判定表与判定树：用“航空行李托运费的计算”说明处理逻辑可用表格或树描述。
2. 职工与职称：职称无进一步性质时可作职工属性；若关联工资、住房、福利，则应作实体。
3. 病人与病房：病房号可作病人属性；若病房还要与医生联系，则病房应作实体。
4. 货物与仓库：一种货物只在一个仓库存放时，仓库号可作属性；若多仓库存放、仓库有面积属性或与职工有管理联系，则仓库应作实体。
5. 销售管理子系统：订单细节应作为实体；订单细节与产品联系；折扣规则应作为实体。
6. 商品销售：实体店零售可用商品、顾客、销售商间联系表示；大宗或网络销售可把合同或订单抽象为实体。
7. 属性域冲突：零件号有的部门定义为整数、有的定义为字符型；年龄有的用出生日期、有的用整数。
8. 属性单位冲突：零件重量可能使用公斤、斤、克等不同单位。
9. 命名冲突：科研项目在不同部门可能称为项目、课题、工程。
10. 结构冲突：职工在一个局部应用中是实体，在另一个局部应用中是属性。
11. 结构冲突集成：零件与产品之间有“构成”联系，产品、零件、供应商之间有“供应”联系，合并时要按语义统一。
12. 冗余数据：`Q3 = Q1 × Q2`、`Q4 = ΣQ5`，因此 Q3、Q4 可消除；相关冗余联系也可消除。
13. 函数依赖表示联系：`职工号 → 部门号` 表示职工属于部门；`(职工号, 产品号) → 工作天数` 表示职工生产产品的工作天数。
14. 负责联系：`负责人.职工号 → 部门号` 和 `部门号 → 负责人.职工号` 表示部门与负责人之间的 1:1 联系。
15. 工厂管理信息系统视图集成：项目与产品异名同义，统一为产品；库存管理中职工与仓库工作关系、职工领导关系可由其他联系导出而取消。
16. m:n 联系转换：选修（学号，课程号，成绩），学号和课程号为组合码。
17. 工厂 E-R 图转换关系模式：部门、职工、产品、供应商、零件、参加、供应等关系模式。
18. 用户视图安全控制：产品关系可为一般顾客建立产品1视图，为销售部门建立产品2视图。
19. 聚簇查询学生：若同一系学生分散在 500 个物理块，至少 500 次 I/O；聚簇存放可显著减少磁盘访问。
20. 数据存放位置：大表可分放在两个磁盘；日志文件与表、索引等数据库对象可放在不同磁盘。
