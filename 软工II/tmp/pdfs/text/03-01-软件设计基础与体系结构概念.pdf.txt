如何应对复杂性？ [SW EBO K 2.1]
 
⼈类认知的局限
7 ± 2 规则（Miller, 1956）：⼈类短期记忆⼀次只能处理 5~9 个信息块
软件系统动辄成百上千个类——远超⼈脑容量

策略 含义 设计中的体现

分解 ⼤问题拆成⼩问题⼦系统、包

设计的复杂度 [SW EBO K 2.1]
两种复杂度
事物复杂度 — 问题域本身的复杂性
载体复杂度 — 软件实现带来的额外复杂性
公式
设计复杂度 = 事物复杂度 + 载体与事物的适配复杂度
好的设计 = 最⼩化适配复杂度

Perry & W olf (1992)：经典公式
 
Software Architecture = { Elements, Forms, Rationale }
 
要素 含义
Elements 组成系统的处理元素、数据元素和连接元素
Forms 元素的组织形式和拓扑结构

--- PAGE 25 ---
Shaw (1995)：部件-连接件-配置模型
 
软件体系结构 = { 部件(Component), 连接件(Connector), 配置(Conﬁguration) }
 
要素 定义 在 Java 中的映射
部件 承载系统主要功能的基本组成单位，包括处理与数据包（Package）、类集合
连接件 定义部件间交互的抽象表示 接⼝（Interface）、事件
配置 定义部件和连接件之间的关联⽅式，组成系统总体结构依赖注⼊、⼯⼚模式

什么是架构⽓味（Architecture Sm ell）？
 
架构⽓味是系统体系结构中可能导致维护困难、性能下降或演化受阻的结构性问题。
 
⽓味类型 描述 后果
循环依赖 A → B → C → A 形成环 ⽆法独⽴编译/部署/测试
God Component ⼀个包/模块承担过多职责 修改波及⾯⼤，测试困难
层违规调⽤ 展示层直接访问数据层 绕过业务规则，安全⻛险
Feature Envy 模块频繁访问另⼀模块的内部数据⾼耦合，应考虑职责迁移
Scattered Functionality 同⼀功能分散在多个模块 修改需同时改多处

ADR —— 架构决策记录 [SW EBO K 2.4]
Architecture Rationale：不仅记录决策，还要记录为什么拒绝其他⽅案
字段 内容
标题 ADR-001: 采⽤三层分层架构
状态 已采纳
背景 在线书店需⽀持 W eb 和移动端，业务逻辑需独⽴于展示
决策 采⽤ Presentation → BusinessLogic → Data 三层架构
理由 分层降低耦合，便于团队并⾏开发，满⾜可维护性需求
被拒绝⽅案 1 微服务架构 — 拒绝理由：团队仅 5 ⼈，⽆ K8s 运维经验
被拒绝⽅案 2 单⽂件脚本 — 拒绝理由：⽆法扩展，⽆法测试
后果 层间通过接⼝通信；跨层调⽤需严格禁⽌
Architecture Rationale 捕获"为什么这样决策"：被考虑的替代⽅案、权衡和拒绝理由

架构技术债务（Architectural Technical Debt）[SW EBO K 2.4]
 
今天的架构决策可能在软件系统的整个⽣命周期中产⽣显著的后续成本。
被推迟的决策可能损害可维护性或未来的可演化性——这些债务终将需要偿还。
 
维度 示例 后果
模块化缺失 初期为赶进度不做分层后续版本开发时间成倍增加
接⼝设计不⾜层间直接引⽤实现类替换数据库需要修改全部代码
⽂档缺失 不写 ADR 新成员⽆法理解架构决策理由
测试缺失 不做集成测试 架构退化⽆法被及时发现
架构技术债务可以⽤视图和视点来分析和管理 [Kruchten 2019]
