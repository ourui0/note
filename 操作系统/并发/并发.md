# 并发

## 多处理器编程

### 多线程编程模型
+ **基本单位：线程（Thread）**：是并发的基本单位，被定义为“共享内存的执行流”
+ **存储结构**：
  + **共享**：全局变量、堆空间（Heap）、代码段。
  + **独享**：寄存器（PC等）、栈（Stack）和栈帧列表、线程元数据（TCB）
+ **状态机视角**：多个线程就像多个共享内存的状态机，调度器仍以选择一个线程执行一步，这可能会在另一个线程不知情的情况下改变其看到的共享状态

### 多线程编程的三大挑战（Heisenbug 根源）

并发程序容易产生难以调试的 Heisenbug，根源在于以下三性的丧失：

| **挑战**           | **定义/后果**                                                | **解决方法**                                  |
| ------------------ | ------------------------------------------------------------ | --------------------------------------------- |
| **原子性丧失**     | 操作被中断或被其他线程干扰，导致“All or nothing”和“Isolation”违背（如 `sum++` 冲突） 。 | 互斥锁（Lock/Unlock） 。                      |
| **顺序性丧失**     | 编译器或处理器为了优化而打乱指令顺序，在多线程下会导致逻辑错误 。 | 内存屏障（Barrier）、`volatile` 关键字、锁 。 |
| **全局一致性丧失** | 现代处理器（如 x86 的 TSO 模型）允许乱序执行，导致不同核心看到的访存顺序不一致 。 | 硬件内存屏障 `__sync_synchronize()`           |

### Pthread

#### 1. 核心 API 概览

| **函数名**           | **功能**           | **核心参数说明**                                             |
| -------------------- | ------------------ | ------------------------------------------------------------ |
| `pthread_create`     | **创建**新线程     | 传入线程号指针、属性、函数入口及参数。                       |
| `pthread_join`       | **等待**并回收线程 | **阻塞**当前线程，直到目标线程结束并回收其资源。             |
| `pthread_exit`       | **终止**当前线程   | 结束执行，并可向 `join` 者传递一个返回码。                   |
| `pthread_yield`      | **让出** CPU       | 建议调度器先运行其他就绪线程，但不阻塞。                     |
| **`pthread_detach`** | **脱离**线程       | **非阻塞**。告诉系统线程结束后立即自动回收资源，不再需要被 `join`。 |

---

#### 2. 代码深度解析

下面通过一段完整的代码示例，展示这些 API 如何协同工作。

```c
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h> // 必须包含此头文件

// 线程执行的函数入口
// 必须返回 void*，且只接受一个 void* 参数
void* thread_work(void* arg) {
    char* name = (char*)arg;
    for (int i = 0; i < 3; i++) {
        printf("线程 %s 正在运行: 步骤 %d\n", name, i);
        
        // 自愿放弃 CPU，让调度器有机会切换到另一个状态机
        sched_yield(); 
    }
    
    // 线程结束，返回一个字符串作为“遗言”
    return "Done!";
}

int main() {
    pthread_t t1, t2; // 线程的“身份证”

    // 1. 创建线程 (pthread_create)
    // 参数：&id, 属性(通常NULL), 函数名, 传递给函数的参数
    pthread_create(&t1, NULL, thread_work, "A");
    pthread_create(&t2, NULL, thread_work, "B");

    void *ret1, *ret2;

    // 2. 等待并回收线程 (pthread_join)
    // 就像父进程 wait 子进程一样，join 保证了资源的回收
    pthread_join(t1, &ret1);
    pthread_join(t2, &ret2);

    printf("线程 A 返回值: %s\n", (char*)ret1);
    printf("线程 B 返回值: %s\n", (char*)ret2);

    return 0;
}
```

```c
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <pthread.h>

void* thread_work(void* arg) {
    char* name = (char*)arg;

    // 方式 B：在线程内部自愿脱离
    // 这样主线程就不需要（也不能）再 join 它了
    pthread_detach(pthread_self());

    for (int i = 0; i < 3; i++) {
        printf("【子线程 %s】步骤 %d\n", name, i);
        usleep(1000);
    }
    printf("【子线程 %s】悄悄地结束了，不带走一片云彩。\n", name);
    return NULL;
}

int main() {
    pthread_t t1, t2;

    printf("【主线程】准备创建两个“脱离”状态的线程...\n");

    pthread_create(&t1, NULL, thread_work, "A");
    pthread_create(&t2, NULL, thread_work, "B");

    // 注意：这里我们不再调用 pthread_join(t1, &ret1)！
    // 因为线程已经 detach 了，如果强行 join，系统会报错。

    printf("【主线程】我不用等它们，我先去干别的事了。\n");

    // 给子线程一点运行时间，否则主线程一旦 return 0，整个进程（包括子线程）都会被强制杀死
    sleep(1);

    printf("【主线程】我也结束了。\n");
    return 0;
}
```

#### 关键点拨：

1. **参数传递**：`pthread_create` 的第四个参数是 `void*`。如果你想传递多个参数，需要定义一个结构体，然后传递结构体的指针。

2. **`join` 的必要性**：如果不 `join`，主线程（Main Thread）可能会在子线程干完活之前就退出了，这会导致整个进程（及其所有线程）被操作系统强制杀掉。

3. **编译命令**：在 Linux 下编译时必须加上 `-lpthread` 参数：

   Bash

   ```
   gcc demo.c -o demo -lpthread
   ```

## 互斥

### 1. 核心概念：为什么需要互斥？

当多个线程同时进入**临界区（Critical Section）**访问共享资源（如全局变量）时，由于指令执行的随机交织，会导致不确定的结果。

- **安全性（Safety）**：确保“坏事不会发生”。在并发中，意味着任何时刻临界区内只能有一个线程。
- **活性（Liveness）**：确保“好事终将发生”。意味着程序不会死锁，最终能跑完。

------

### 2.尝试方案1：关中断（仅单处理器有效）

```c
// 伪代码：通过开关中断实现原子性
void lock() {
    disable_interrupts(); // 关闭中断（特权指令）
}
void unlock() {
    enable_interrupts(); // 开启中断
}
```

**问题**：

+ 用户态程序无法执行关中断（需操作系统权限）。
+ 多处理器无效（每个CPU有独立中断状态）。
+ 若临界区死循环，整个系统卡死。

---

### 3. 尝试方案 2：纯软件实现（自旋锁初探）

我们最初的想法可能是用一个简单的标志位 `flag` 来标记资源是否被占用：

```c
int flag = 0; // 0 表示空闲，1 表示被占用

void lock() {
    while (flag == 1); // 如果有人在用，我就死循环等（自旋）
    flag = 1;          // 抢占资源
}

void unlock() {
    flag = 0;          // 释放资源
}
```

**失败原因**：`lock()` 函数本身不是原子的。

> 如果线程 A 刚跳出 `while` 循环，还没来得及执行 `flag = 1`，操作系统就切换到了线程 B。此时线程 B 发现 `flag` 也是 0，也会跳出循环。最终两个线程都进入了临界区。

------

### 4.尝试方案 3 ：互斥的test

如果每个线程都是采⽤同⼀个判定：test flag == 1，那么完全存在所有的线程都可能得到同样的True

但是如果我们给每个线程的判定条件都不⼀样，且判定条件不可能同时对每个为True呢？ —> ⼀个线程回答“True”意味着其他线程回答“False”，在逻辑上就达成了互斥！

```c
#for thread 1
void lock(){ 
 while (flag == 0); //⾃旋的观测flag
} 
void unlock(){ 
 flag = 0; //设置
} 
void task(){ 
 while(1){ 
 lock(); 
 critical_section_code(); 
 unlock(); 
 } 
}
```

**失败原因：**如果thread 2始终不进⼊临界区，那么thread 1最多进⼊⼀次临界区之后就⽆法再进⼊了, 违背了[liveness]性质，因为⽬前没

有线程在临界区，⽽thread 1想进⼊临界区，但永远⽆法再进⼊，因此⽆法“⾏进”！

### 5. 尝试方案 4 ：Peterson 算法初尝试

```c
int intents[2] = {0, 0}; //进⼊意图
int flag = 0; // 当前是谁可以获得锁 (thread 0 or 1)
int self = i; //当前的线程ID，0， 1中的⼀个
void lock() { 
 intents[self] = 1; // 标记⾃⼰想要进⼊临界区
 while ( (intents[(self + 1)%2] == 1) //别⼈想不想要进来
 && (flag == self) ); // 如果别⼈也想进来，就再看看是否当前“轮转”到⾃⼰了
} 
void unlock() { 
 intents[self] = 0; //标记⾃⼰不再想要进⼊临界区
 flag = self; //轮转到下⼀位
}
```

**失败原因：**这个错误的实现将Peterson算法中用于实现“谦让”和“裁决”的核心变量 `flag`的用法完全搞反了，导致算法失去了协调两个线程有序、互斥访问临界区的全部能力。

### 7. 终极方案：硬件提供的原子操作

为了解决上述问题，现代 CPU 提供了**原子指令**。在 x86 架构中，最核心的是 `lock cmpxchg`（Compare and Exchange）。它在硬件层面保证了“检查-修改”这两步是一气呵成的。

#### x86 下的自旋锁实现（汇编级）

讲义中展示了利用硬件原子性实现的锁：

```c
int flag = 0; 

void lock() {
    int expected;
    do {
        expected = 0; // 期待当前 flag 是 0
        // 原子指令：如果 flag == expected (0)，则把 flag 设为 1
        asm volatile (
            "lock cmpxchg %2, %1"
            : "+a" (expected)
            : "m" (flag), "r" (1)
            : "memory", "cc"
        );
        // 如果 flag 原本不是 0，expected 会被更新为 flag 的当前值，循环继续
    } while (expected != 0); 
}

void unlock() {
    // 释放锁只需要原子地把 flag 写回 0
    asm volatile ("mov %1, %0" : "=m" (flag) : "r" (0) : "memory");
}
```

## 互斥_进阶

------

### 一、 互斥的基石：自旋锁的演进与公平性

自旋锁（Spinlock）是实现互斥的最基础机制。它的核心思想非常直接：当线程尝试获取一个已被占用的锁时，它不会放弃 CPU，而是通过一个 `while` 循环不断地检查（自旋）锁是否已经被释放。

#### 1. 基础自旋锁及其“饥饿”问题

**原理解析：**

基础自旋锁依赖于硬件提供的原子操作（如 `Test-And-Set` 或 `Exchange`）。虽然它能保证互斥，但存在一个致命缺陷：**无法保证公平性（有界等待）**。当多个线程同时自旋等待一把锁时，一旦锁被释放，哪个线程能抢到锁完全取决于操作系统的调度策略和微观层面的时序。这可能导致某些运气不佳的线程永远抢不到锁，产生“饥饿”现象。

**代码实现：**

```c
// 基础自旋锁 (存在公平性问题)
typedef struct lock {
    int locked; // 0 表示空闲，1 表示被占用
} lock_t;

void lock(lock_t *lk) {
    // __sync_lock_test_and_set 是原子操作：将 locked 设为 1，并返回旧值
    // 如果返回 1，说明锁原本就被占着，继续自旋；返回 0 说明抢到了锁
    while (__sync_lock_test_and_set(&lk->locked, 1) == 1) {
        // 自旋等待（Busy-waiting），持续消耗 CPU 周期
    }
}

void unlock(lock_t *lk) {
    // 释放锁，将 locked 设回 0
    __sync_lock_release(&lk->locked);
}
```

#### 2. 排号自旋锁（Ticket Lock）：解决公平性

**原理解析：**

为了解决饥饿问题，计算机科学家引入了排队机制，即**排号自旋锁（Ticket Lock）**。它的原理与去银行柜台办事完全一样：

1. **领号（Ticket）**：每个尝试加锁的线程，原子地获取一个递增的票号。

2. **叫号（Turn）**：锁内部维护一个“当前服务号”。线程不断比对自己的票号和当前服务号，如果不一致就自旋；一旦一致，说明轮到自己进入临界区。

3. **办完（Unlock）**：离开临界区时，将“当前服务号”原子地加一，呼叫下一个排队的线程。

   这种机制通过 `Fetch-And-Add` 原子指令，完美实现了先来先服务（FIFO）。

**代码实现：**

```c
// 排号自旋锁 (Ticket Lock) - 保证绝对公平
typedef struct lock_ticket {
    int ticket; // 下一个将被发放的“排队号码”
    int turn;   // 当前正在被服务的“叫号号码”
} lock_t;

void lock(lock_t *lk) {
    // 原子地领取一个号码，将 ticket 加 1，并返回加 1 前的旧值作为“我的号码”
    int myturn = __sync_fetch_and_add(&lk->ticket, 1);
    
    // 自旋等待，直到“当前服务号”等于“我的号码”
    while (lk->turn != myturn) {
        // 自旋等待
    }
}

void unlock(lock_t *lk) {
    // 原子地将“当前叫号”加 1，允许排在后面的下一个线程进入
    __sync_fetch_and_add(&lk->turn, 1);
}
```

### 二、 内核态的特殊挑战：自旋锁与中断的冲突

在操作系统内核中实现互斥，面临着用户态程序所没有的复杂性：硬件中断。

**原理解析：**

假设内核线程 A 拿到了自旋锁，正在访问内核共享数据。突然，时钟中断或磁盘中断到来，CPU 强制暂停线程 A，转去执行中断处理程序。糟糕的是，这个中断处理程序恰好也需要获取同一把自旋锁。

由于中断处理程序的优先级通常高于普通线程，它会不断自旋等待锁释放；而持有锁的线程 A 被暂停了，永远无法去释放锁。这就造成了**死锁**。

**解决方案：**

在内核中获取自旋锁之前，**必须先关闭本地 CPU 的中断**。但我们不能粗暴地“关中断 -> 拿锁 -> 开中断”，因为线程在加锁前可能已经处于关中断状态，粗暴的开中断会破坏原有的系统状态。正确的做法是：**保存加锁前的中断状态，解锁时精确恢复**。在 xv6 等教学操作系统中，通常通过维护关中断的嵌套层级来实现。

**代码实现（概念模型）：**

```c
// 模拟操作系统的自旋锁结构
typedef struct spinlock {
    int locked;
    int intena;   // 记录加锁前，中断是否是开启状态
    int noff;     // 记录关中断的嵌套深度 (处理多次连续加锁的情况)
} spinlock_t;

// 获取锁
void acquire(spinlock_t *lk) {
    push_off(); // 关键步骤：关闭中断，并增加嵌套深度 noff。如果是第一次关中断，还会记录当前的 intena 状态。
    
    while (__sync_lock_test_and_set(&lk->locked, 1) == 1) {
        // 在关闭中断的安全环境下自旋等待
    }
}

// 释放锁
void release(spinlock_t *lk) {
    __sync_lock_release(&lk->locked); // 先释放锁
    
    pop_off(); // 关键步骤：减少关中断嵌套深度 noff。如果嵌套深度降为 0，且 intena 记录原本是开中断的，则真正开启硬件中断。
}
```

### 三、 用户态的性能演进：从主动让步到操作系统协同

在用户态，如果临界区很长，自旋锁会让等待的线程白白消耗 CPU（空转）。若持有锁的线程被操作系统挂起，等待者的自旋浪费将极其严重。

#### 1. 简单让出 CPU (Yielding)

**原理解析：**

最直接的优化思路是：如果在自旋中发现锁被占用，就不空转了，主动调用系统调用（如 `sched_yield()`）把 CPU 让给别的线程。

**缺陷：** 这种做法虽然减少了空转，但如果竞争激烈，大量线程会在“就绪队列”和“运行态”之间疯狂切换。上下文切换的开销极大，依然治标不治本。

**代码实现：**

```c
// 简单“让出CPU”锁 (存在大量上下文切换开销)
void yield_lock(spinlock_t *lk) {
    while (__sync_lock_test_and_set(&lk->locked, 1) == 1) {
        sched_yield(); // 发现锁被占，主动陷入内核让出 CPU 调度权
    }
}
```

#### 2. 理想的协同方案：阻塞与唤醒 (Blocking & Waking)

**原理解析：**

更好的方案是与操作系统协同：拿不到锁的线程将自己**阻塞（Sleep）**，放入该锁的等待队列中，彻底交出 CPU；持有锁的线程在释放锁时，负责从等待队列中**唤醒（Wakeup）**一个线程。

**缺陷（唤醒丢失竞态）：** 纯用户态加锁和系统调用睡眠之间存在“时间差”。如果在准备睡眠但还没真正睡眠的瞬间，锁被释放并且执行了唤醒操作，这个唤醒信号就会丢失。随后线程真正进入睡眠，可能永远不会被再次唤醒。

**代码实现（带有竞态缺陷的伪代码）：**

```c
void mutex_lock(mutex_t *lk) {
    int got;
    do {
        got = atomic_xchg(&lk->status, LOCKED); // 尝试拿锁
        if (got != UNLOCKED) {
            // 【竞态风险点】：如果在此刻发生上下文切换，持有锁的线程执行了 unlock 并触发 wakeup。
            // 但当前线程还没真正 sleep，这个 wakeup 就白发了（唤醒丢失）。
            wait(lk->wait_list); // 阻塞自己
        } else {
            break; // 拿到了锁
        }
    } while (1);
}

void mutex_unlock(mutex_t *lk) {
    atomic_xchg(&lk->status, UNLOCKED); // 释放锁
    if (!is_empty(lk->wait_list)) {
        wakeup(lk->wait_list); // 唤醒等待者
    }
}
```

### 四、 现代互斥的终极形态：Linux Futex 与两阶段锁

为了解决上述“唤醒丢失”的问题，同时兼顾极致的性能，Linux 引入了 **Futex (Fast Userspace muTexes)** 机制。

**原理解析：**

Futex 的核心理念是**两阶段锁（Two-Phase Locking）**：

1. **快速路径 (Fast Path)**：在没有竞争的绝大多数情况下，只需在用户态执行一次原子指令即可拿到锁，开销极小，**绝不陷入内核**。
2. **慢速路径 (Slow Path)**：只有发生真正的锁竞争时，才通过 `futex` 系统调用陷入内核。`futex_wait(address, expected)` 系统调用在内核层面保证了：**只有当 `address` 内存地址里的值依然等于 `expected` 时，线程才会安全地进入休眠**。这就从根本上杜绝了检查和休眠之间的“唤醒丢失”竞态。

**代码实现（Futex 核心思想展示）：**

```c
#define UNLOCK 0
#define LOCKED_NO_WAITERS 1
#define LOCKED_WITH_WAITERS 2

void mutex_lock(int *futex) {
    int c;
    
    // 【快速路径】：期望当前是 UNLOCK(0)，尝试原子地修改为 LOCKED_NO_WAITERS(1)
    c = cmpxchg(futex, UNLOCK, LOCKED_NO_WAITERS);
    if (c == UNLOCK) {
        return; // 抢锁成功，纯用户态操作，极速返回！
    }

    // 【慢速路径】：锁被占用，发生竞争
    while (1) {
        // 尝试将锁状态升级为“带有等待者 (2)”
        if (c == LOCKED_WITH_WAITERS ||
            cmpxchg(futex, LOCKED_NO_WAITERS, LOCKED_WITH_WAITERS) != 0) {
            
            // 关键系统调用：如果 futex 的值依然是 2 (LOCKED_WITH_WAITERS)，则安全阻塞。
            // 操作系统内核会保证这里的原子性，消除唤醒丢失问题。
            futex_wait(futex, LOCKED_WITH_WAITERS);
        }
        
        // 被唤醒后，重新尝试获取锁
        c = cmpxchg(futex, UNLOCK, LOCKED_WITH_WAITERS);
        if (c == UNLOCK) {
            return;
        }
    }
}

void mutex_unlock(int *futex) {
    // 【快速路径】：原子递减，如果没有等待者（值从 1 变回 0），直接纯用户态返回
    if (atomic_dec(futex) == LOCKED_NO_WAITERS) {
        return;
    }
    
    // 【慢速路径】：有等待者被阻塞了，需要将状态重置为 UNLOCK(0)，并陷入内核唤醒它们
    atomic_set(futex, UNLOCK);
    futex_wake(futex, 1); // 唤醒 1 个等待线程
}
```

*(注：日常开发中，我们不需要手写这些复杂逻辑，POSIX 线程库提供的 `pthread_mutex_lock/unlock` 在 Linux 底层正是基于 Futex 机制实现的。)*

### 五、 并发数据结构实践：从粗粒度到细粒度

理解了锁的底层实现后，如何使用锁同样关键。文档以并发计数器为例，揭示了“锁粒度”对性能的巨大影响。

**原理解析：**

- **粗粒度锁（一把大锁）**：用一把锁保护整个数据结构。实现简单，绝对正确，但会把多线程程序的并发执行强行变成“串行执行”，性能极差。
- **细粒度锁（分层/懒惰计数器 - Sloppy Counter）**：为每个 CPU 核心分配一个独立的“本地计数器”和“本地锁”。线程只操作自己所在 CPU 的本地计数器，彼此互不干扰，实现了真正的并行。当本地计数达到一定阈值时，才去获取一次“全局锁”，将本地数据同步给全局计数器。这极大地减少了锁的争用。

**代码实现：**

```c
// 1. 性能受限的粗粒度计数器 (全局大锁)
typedef struct counter_t {
    int value;
    pthread_mutex_t lock;
} counter_t;

void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock); // 所有线程都在这里排队
    c->value++;
    pthread_mutex_unlock(&c->lock);
}

// ---------------------------------------------------------

// 2. 高性能的分层计数器 (Sloppy Counter)
#define NUM_CPUS 4
typedef struct counter_approx_t {
    int global_value;                   // 全局精确值
    pthread_mutex_t global_lock;        // 保护全局值的锁
    
    int local_values[NUM_CPUS];         // 每个 CPU 的本地缓存值
    pthread_mutex_t local_locks[NUM_CPUS]; // 保护本地值的锁
    
    int threshold;                      // 同步阈值
} counter_approx_t;

void increment_local(counter_approx_t *c, int cpu_id) {
    // 绝大多数情况下，只竞争当前 CPU 的本地锁，非常快
    pthread_mutex_lock(&c->local_locks[cpu_id]);
    c->local_values[cpu_id]++;
    
    // 当本地积累的数量达到阈值 S 时，才去竞争全局锁
    if (c->local_values[cpu_id] >= c->threshold) {
        pthread_mutex_lock(&c->global_lock);
        c->global_value += c->local_values[cpu_id]; // 批量同步到全局
        pthread_mutex_unlock(&c->global_lock);
        
        c->local_values[cpu_id] = 0; // 本地清零
    }
    pthread_mutex_unlock(&c->local_locks[cpu_id]);
}
```
