逻辑视⻆与包的概念
逻辑视⻆
关注系统的功能组织
描述系统的静态结构

⽬标：⾼内聚、低耦合

UML 中的分组机制
将相关的类/接⼝组织在⼀起
对应 Java 中的 package
包之间存在依赖关系
包是体系结构逻辑视⻆的基本构造单元，好的包划分直接决定系统的可维护性。

包设计原则 — 内聚性三原则
原则 全称 含义
REP 重⽤-发布等价原则重⽤的粒度 = 发布的粒度
CRP 共同重⽤原则 ⼀起被重⽤的类放同⼀个包
CCP 共同封闭原则 因同⼀原因变更的类放同⼀个包
书店案例
REP：entity 包整体发布，Book 和 Order ⼀起被所有层引⽤
CRP：BookDao 和 BookService 总是⼀起使⽤ → 放在同⼀业务模块下
CCP：⽀付需求变更只影响 payment 模块，不波及 book 模块
9


--- PAGE 10 ---
包设计原则 — 耦合性三原则
原则 全称 含义
ADP ⽆环依赖原则包之间的依赖关系不能形成环
SDP 稳定依赖原则依赖⽅向朝着更稳定的包
SAP 稳定抽象原则越稳定的包应越抽象
书店案例
ADP：controller → service → dao，⽆环
SDP：entity 最稳定（很少变化），所有层都依赖它
SAP：dao 包对外暴露的是接⼝（抽象），实现类放在 dao.impl 中

--- PAGE 11 ---
REP 重⽤-发布等价原则 [Robert C. M artin]
The granule of reuse is the granule of release.
重⽤的单元 = 发布的单元。
 
含义
如果你要复⽤⼀个包中的某个类，你就得依赖整个包
因此，包中的类必须有理由被⼀起重⽤
案例：在线书店
包 是否满⾜ REP 理由
entity （Book, O rder, Customer...） 满⾜ 所有层都引⽤ entity，整体发布
假如把 Book 和 PaymentGateway 放同⼀包 违反 ⽤图书搜索功能不需要⽀付⽹关
11


--- PAGE 12 ---
CRP 共同重⽤原则 [Robert C. M artin]
Classes that are used together belong together.
⼀起被使⽤的类应放在⼀起。
 
含义
CRP 告诉我们哪些类不该放在⼀起：如果⽤了包中 A 类但不需要 B 类，说明 A 和 B 不该在同⼀个包
案例：连锁超市
功能 对应逻辑包 CRP 分析
销售 SalesUI, Sales, SalesData 三个总是⼀起使⽤ ✓
库存 CommodityUI, Commodity, CommodityData 三个总是⼀起使⽤ ✓
销售+库存放⼀个包？违反 CRP 修改库存时被迫重新测试销售
12


--- PAGE 13 ---
CCP 共同封闭原则 [Robert C. M artin]
Classes that change together belong together.
因同⼀原因变化的类应放在⼀起（包级别的 SRP）。
 
含义
当需求变更时，变更应该集中在尽可能少的包中
违反 CCP = ⼀次需求变更要改多个包 = ⾼维护成本
案例：在线书店
需求变更："⽀付⽅式新增微信⽀付"
如果按 CCP 划分 变更范围
service.payment + dao.payment 只改 2 个包 ✓
如果⽀付和订单混在⼀起 改动波及订单逻辑 ✗

--- PAGE 14 ---
CCP 与 CRP 的权衡 [Robert C. M artin]
 
CCP 和 CRP 是互斥的 —— 不可能同时完美满⾜两者。
 
维度 CCP（共同封闭） CRP（共同重⽤）
服务对象 维护者（Maintainers） 重⽤者（Reusers）
包的⼤⼩ 倾向让包更⼤（变更集中）倾向让包更⼩（减少不必要依赖）
优先场景 项⽬早期：需求频繁变更 项⽬成熟期：对外发布/复⽤
 
项⽬⽣命周期中的演进策略
早期：以 CCP 为主导 → ⼤包、便于开发和维护
后期：架构稳定后，重构包结构 → 以 CRP 为主导，⽅便外部复⽤
没有"正确答案"，只有当前阶段最合适的权衡
14


--- PAGE 15 ---
SDP 稳定依赖原则 [Robert C. M artin]
Depend in the direction of stability.
依赖⽅向应朝着更稳定的⽅向。
 
怎么判断稳定性？
稳定 = 很多包依赖它（被需要）→ 改动代价⼤ → 不容易变
不稳定 = 它依赖很多包 → 容易变
案例：不稳定度计算
包 Ca(传⼊)Ce(传出)I = Ce/(Ca+Ce) 稳定性
entity 4 0 0.00 最稳定 — 正确！
controller 0 3 1.00 最不稳定 — 正确！
service 1 2 0.67 中等
controller（不稳定）→ service（中等）→ dao → entity（稳定） ✓  符合 SDP

--- PAGE 16 ---
SAP 稳定抽象原则 [Robert C. M artin]
A package should be as abstract as it is stable.
越稳定的包应越抽象；越不稳定的包应越具体。
 
SDP + SAP = 依赖倒置原则（DIP）在包级别的体现
包 稳定度 应有的抽象度 实际做法
entity 最稳定 (I=0) ⾼抽象 PO JO ，⽆实现细节 ✓
dao （接⼝包） 较稳定 ⾼抽象 只有 interface ✓
controller 最不稳定 (I=1) 低抽象 全是具体实现 ✓
service （接⼝包）中等 中等 interface + 部分实现 ✓
痛苦区：稳定但具体（改不动但想改） → 要重构为接⼝
⽆⽤区：不稳定但抽象（没⼈⽤的接⼝） → 可以删除

--- PAGE 38 ---
接⼝在体系结构中的作⽤
"楼板"⽐喻
  ┌─────────────┐  ← 上层（使⽤者）
  │  controller  │
  ├═════════════╡  ← 接⼝  = " 楼板 "
  │  service     │
  ├═════════════╡  ← 接⼝  = " 楼板 "
  │    dao       │
  └─────────────┘
接⼝是层与层之间的契约，如同楼板将楼层隔离。
接⼝的三⼤好处
1. 解耦：上层不依赖下层实现
2. 可替换：实现类可以随时替换
3. 可测试：⽤ Mock 替代真实实现
先定义接⼝，再编写实现 — 这就是⾯向接⼝编程。

--- PAGE 39 ---
PO  与 VO  概念
概念 全称 ⽤途 所在层
PO Persistent O bject 与数据库表⼀⼀对应 entity / dao
VO Value O bject ⾯向展示层的数据传输对象controller / service
为什么需要区分？
PO  包含数据库细节（主键、外键、时间戳）
VO  只包含前端需要的字段
隔离变化：数据库字段变更不影响前端接⼝
// PO: 对应  book 表
public class Book { Long id; String isbn; String title; BigDecimal price; ... }
// VO: 前端展示⽤
public class BookVO { String isbn; String title; String priceText; double rating; }

--- PAGE 40 ---
依赖倒置原则（DIP）详解
传统依赖
⾼层模块  ── 依赖 ──  低层模块
  (service)          (dao 实现 )
⾼层直接依赖低层具体实现，耦合度⾼。
依赖倒置后
⾼层模块  ── 依赖 ──  抽象接⼝
                      ▲
低层模块  ── 实现 ──┘
⾼层和低层都依赖抽象，依赖⽅向"倒置"。
DIP 两条规则：
1. ⾼层模块不应依赖低层模块，两者都应依赖抽象
2. 抽象不应依赖细节，细节应依赖抽象

案例：BookServiceImpl — 构造器注⼊
@Service
public class BookServiceImpl implements BookService {
    private final BookDao bookDao;
    // 构造器注⼊  — Spring 推荐⽅式
    @Autowired
    public BookServiceImpl(BookDao bookDao) {
        this.bookDao = bookDao;
    }
    @Override
    public BookVO findById(Long id) {
        Book book = bookDao.findById(id);
        return convertToVO(book);
    }
    @Override
    public boolean checkStock(Long bookId, int quantity) {
        Book book = bookDao.findById(bookId);
        return book != null && book.getStock() >= quantity;
    }
}
BookServiceImpl 依赖 BookDao 接⼝，不依赖具体实现类。

接⼝设计⼩结
设计要点 说明
接⼝ = 契约 定义层间交互的 W hat，隐藏 How

集成策略对⽐
策略 ⽅式 优点 缺点

体系结构评审⽅法
ATAM
Architecture Tradeoﬀ Analysis Method
分析质量属性之间的权衡
输⼊：架构⽂档 + 质量属性场景
输出：⻛险点、权衡点、敏感点
适⽤于⼤型系统早期评审
SAAM
Software Architecture Analysis Method
基于场景的分析⽅法
将场景分为直接场景和间接场景
评估架构对场景的⽀持程度
较 ATAM 更简单，适合中⼩型项⽬
两种⽅法都强调：在编码之前发现架构问题，修复成本远低于编码之后。

架构度量指标 [SW EBO K 4.4]
包级度量
指标 公式 含义
Ca (传⼊依赖)依赖本包的外部包数越⾼越稳定
Ce (传出依赖)本包依赖的外部包数越⾼越不稳定
I (不稳定度)Ce / (Ca + Ce) 0=完全稳定, 1=完全不稳定
A (抽象度) 抽象类数 / 总类数 接⼝包→⾼, 实现包→低
案例：在线书店包度量
包 Ca Ce I A 评估
entity 4 0 0.00 0.0 最稳定，符合 SDP
dao (接⼝) 2 1 0.33 1.0 稳定+抽象，符合 SAP
service (接⼝)1 2 0.67 1.0 接⼝抽象，依赖适中
controller 0 3 1.00 0.0 最不稳定，只有实现
DevO ps 度量：变更前置时间、部署频率、MTTR、变更失败率——也是架构健康度的指标
